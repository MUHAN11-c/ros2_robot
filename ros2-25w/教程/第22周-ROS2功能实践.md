## 22.2 知识点梳理

### 22.2.1 第1课 机器人组成、控制系统远程开发环境（1h04m · 8 节）

- **核心概念**：机器人（Robot）= 机械结构 + 控制系统 + 感知系统 + 能源系统的有机整体；远程开发（Remote Development）= 开发机与运行机分离，代码在 PC 上编辑/编译，节点在机器人上运行。
- **机器人组成**：

  | 组成 | 典型部件 | 在 ROS2 中的对应 |
  |---|---|---|
  | 机械结构 | 底盘（差速/阿克曼/全向）、机械臂、云台 | URDF/xacro 模型、`robot_state_publisher` |
  | 控制系统 | 主控板（Jetson/树莓派/工控机）、电机驱动、STM32 | ROS2 节点、`/cmd_vel`、串口/底盘驱动包 |
  | 感知系统 | 激光雷达、相机、IMU、GNSS、超声波 | `sensor_msgs` 消息族、驱动节点 |
  | 能源系统 | 电池、电源管理、稳压模块 | `/battery_state`（`sensor_msgs/BatteryState`） |

- **远程开发概述**：场景是机器人算力有限、不便接显示器键盘；作用是开发效率与调试便利；实现方式包括 SSH 终端、VSCode Remote - SSH、共享文件系统/NFS、`colcon build` 后 rsync 部署等。
- **SSH 环境搭建**：机器人端 `sudo apt install openssh-server && sudo systemctl enable --now ssh`；PC 端 `ssh user@<机器人IP>`；建议用密钥免密（`ssh-keygen` + `ssh-copy-id`），并在同一局域网下确认 `ROS_DOMAIN_ID` 一致，才能在 PC 上 `ros2 node list` 看到机器人上的节点。
- **要点 · 远程开发的 ROS2 特有坑**：DDS（数据分发服务）默认走 UDP 组播发现，跨网段/VPN 下节点互不可见；可用 `ROS_LOCALHOST_ONLY=1` + SSH 端口转发，或配置 `FASTRTPS_DEFAULT_PROFILES_FILE` 指定单播 peer。

### 22.2.2 第2课 底盘使用与里程案例分析与实现（1h57m · 14 节）

- **核心概念**：里程计（Odometry）是机器人根据轮速/编码器推算自身位姿的过程与结果，是导航中 `odom → base_link` 变换的来源；本课案例目标是「订阅 `/odom`，把历史位姿串成轨迹（Path）并发布」。
- **要点 1 · 里程计接口消息**：`nav_msgs/Odometry` 关键字段：

  | 字段 | 含义 |
  |---|---|
  | `header.stamp` / `header.frame_id` | 时间戳 / 位姿所在坐标系（通常 `odom`） |
  | `child_frame_id` | 位姿描述的对象（通常 `base_link`） |
  | `pose.pose.position` / `orientation` | 位置（m）与姿态四元数 |
  | `twist.twist.linear` / `angular` | 机体坐标系下的线速度与角速度 |
  | `pose.covariance` / `twist.covariance` | 6×6 协方差，融合（EKF）时的权重依据 |

- **要点 2 · 路径相关消息接口**：`nav_msgs/Path` = `header` + `geometry_msgs/PoseStamped[] poses`；`PoseStamped` = `header` + `pose`。整条轨迹的坐标系由 `Path.header.frame_id` 统一声明，rviz2 的 Path 显示插件按它做 tf 变换。
- **要点 3 · C++ 案例八步走**：① 框架搭建（订阅 `/odom`、发布 `/path`、保存历史点）→ ② 计算当前点与轨迹末点的欧氏距离 → ③ 距离超阈值才追加（避免轨迹点爆炸）→ ④ 发布并测试 → ⑤ 修复 BUG（典型：坐标系不一致、时间戳未同步、轨迹点无限增长）→ ⑥ rviz2 修改 Path 样式（颜色/线宽/保留点数）→ ⑦ 移植实体机器人（改话题名、加 QoS、确认里程计来源）→ ⑧ 小结。
- **要点 4 · Python 案例**：逻辑与 C++ 版一致——计算距离（`math.dist` / `numpy.linalg.norm`）、条件追加、组织 `Path` 并发布；体会 rclpy 与 rclcpp 在消息构造、回调签名上的差异。
- **要点 5 · 硬件平台小结**：实体机器人上里程计由底盘驱动（编码器积分 + 运动学解算）发布；差速底盘轮速 → 速度的解算依赖轮距与轮半径，二者标不准就会让轨迹「画歪」（第23 周的标定内容由此引出）。

### 22.2.3 第3课 传感器之激光雷达详解与仿真案例（3h44m · 26 节）

- **核心概念**：激光雷达（LiDAR，Light Detection and Ranging）通过测量激光束的往返时间/相位得到距离，输出一圈（2D）或多圈（3D）测距点，是 SLAM 与导航最主要的环境感知传感器。
- **要点 1 · 特点与分类**：按线数分单线（2D 扫描，如 RPLIDAR、思岚）与多线（16/32/64 线，如 Velodyne、禾赛）；按测距原理分 TOF（飞行时间）与三角测距；关键指标：测距范围、精度、采样频率（Hz）、角分辨率、点频。
- **要点 2 · 单线雷达基本使用与 laserscan 插件**：真机端安装驱动（如 `rplidar_ros`）后发布 `/scan`；仿真端在 URDF/Gazebo 中用 `laserscan`（ray / gpu_ray）插件生成 `sensor_msgs/LaserScan`，需配置采样数、角范围、噪声等参数。
- **要点 3 · LaserScan 消息接口（上下两讲）**：

  | 字段 | 含义 |
  |---|---|
  | `angle_min` / `angle_max` | 扫描起始/终止角（rad） |
  | `angle_increment` | 相邻测距点角间隔（rad） |
  | `time_increment` / `scan_time` | 点间/整圈耗时（s） |
  | `range_min` / `range_max` | 有效测距范围（m） |
  | `ranges[]` | 第 i 点距离 = `angle_min + i * angle_increment` 方向上的距离 |
  | `intensities[]` | 反射强度，可选 |

  > **注意：** `ranges[i]` 出现 `inf`（超出量程）或 `nan`（无效返回）是常态，写处理逻辑时必须先判 `math.isfinite(r)`，否则 SLAM 与避障都会被脏数据带偏。

- **要点 4 · 单线仿真案例（C++ 三讲 + Python 一讲）**：案例需求是「在仿真中发布一条符合 `LaserScan` 语义的扫描数据」，流程：分析消息字段 → C++ 框架搭建（定时器 + 发布者）→ 核心逻辑（按角分辨率填充 `ranges`，模拟前方障碍距离场）→ 结果优化（加噪声、加 `intensities`、校正 `frame_id`）→ Python 版完整实现。
- **要点 5 · 多线雷达**：基本使用三步——软件安装与配置（点云驱动/仿真插件）、硬件准备与配置（供电、网口、IP 如 192.168.1.201）、启动并测试（`roslaunch`/`ros2 launch` 后 rviz2 加 PointCloud2 显示）。
- **要点 6 · 点云接口**：`sensor_msgs/PointCloud2` 用「二进制大数组 + 字段描述」表达 N 个点：`height/width` 组织成有序/无序点云，`fields[]`（`PointField`：name/offset/datatype/count）描述 x、y、z、intensity、ring 等通道，`point_step` 为单点字节数、`row_step` 为单行字节数，`data[]` 为原始字节。多线仿真案例即按此结构组织点云：① 框架 → ② 组织基本参数（宽高、字段、步长）→ ③ 遍历扫描点 → ④ 设置每个扫描点的 x/y/z（按线数、水平角、垂直角、距离解算）→ ⑤ 优化小结；Python 版同样三步完成并发布。
- **要点 7 · 调试习惯**：先 `ros2 interface show sensor_msgs/msg/LaserScan`，再 `ros2 topic echo /scan --field ranges | head` 快速看数据流；点云用 `ros2 topic hz /points` 确认帧率是否达到预期（多线雷达常因网络/USB 带宽掉帧）。

## 22.3 重点与难点

1. **Odometry 的坐标系约定**：`header.frame_id` 是「位姿所在系」（odom），`child_frame_id` 是「被描述对象」（base_link）。填反会导致 tf 树断链或反向，rviz2 中机器人「倒着走」。
2. **轨迹点的稀疏化**：每个 `/odom` 回调都往 `Path.poses` 里塞点，几分钟就会积累上万点、拖垮 rviz2。必须按「距上一轨迹点超过阈值才追加」过滤，并给 `poses` 设上限。
3. **LaserScan 的角度语义**：`ranges[i]` 的方向角是 `angle_min + i * angle_increment`，且坐标系遵循右手系（x 前、y 左、z 上）；角度搞反，避障方向就反。
4. **PointCloud2 的内存布局**：它是「裸字节数组 + 元信息」，没有现成的 `points[i].x`。C++ 用 `sensor_msgs::PointCloud2Iterator<float>` 最稳妥；直接 `memcpy` 填充时务必算清 `point_step` 与各字段 `offset`。
5. **仿真 → 实机迁移**：话题名（`/scan` vs `/rplidar/scan`）、QoS（传感器数据用 `SensorDataQoS`）、`frame_id` 与 URDF 链杆名一致性，是三类最常见的移植故障。

### 22.4.2 场景 2：里程计轨迹节点（C++，包 `odom_path_pkg`，文件 `src/odom_path_node.cpp`）

```cpp
#include <memory>
#include <vector>
#include <cmath>
#include "rclcpp/rclcpp.hpp"
#include "nav_msgs/msg/odometry.hpp"
#include "nav_msgs/msg/path.hpp"
#include "geometry_msgs/msg/pose_stamped.hpp"

class OdomPathNode : public rclcpp::Node {
public:
  OdomPathNode() : Node("odom_path_node") {
    path_pub_ = create_publisher<nav_msgs::msg::Path>("/path", 10);
    odom_sub_ = create_subscription<nav_msgs::msg::Odometry>(
        "/odom", 10,
        std::bind(&OdomPathNode::onOdom, this, std::placeholders::_1));
    path_.header.frame_id = "odom";   // 整条轨迹统一在 odom 坐标系下
  }

private:
  void onOdom(const nav_msgs::msg::Odometry::SharedPtr msg) {
    const auto & p = msg->pose.pose.position;
    // 距离上一轨迹点过近则丢弃，稀疏化轨迹
    if (!path_.poses.empty()) {
      const auto & q = path_.poses.back().pose.position;
      if (std::hypot(p.x - q.x, p.y - q.y) < 0.05) {  // 5 cm 阈值
        return;
      }
    }
    geometry_msgs::msg::PoseStamped ps;
    ps.header = msg->header;           // 复用时间戳与坐标系
    ps.pose = msg->pose.pose;
    path_.poses.push_back(ps);
    if (path_.poses.size() > 2000) {   // 上限保护
      path_.poses.erase(path_.poses.begin());
    }
    path_.header.stamp = now();
    path_pub_->publish(path_);
  }
  rclcpp::Publisher<nav_msgs::msg::Path>::SharedPtr path_pub_;
  rclcpp::Subscription<nav_msgs::msg::Odometry>::SharedPtr odom_sub_;
  nav_msgs::msg::Path path_;
};

int main(int argc, char ** argv) {
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<OdomPathNode>());
  rclcpp::shutdown();
  return 0;
}
```

### 22.4.3 场景 3：里程计轨迹节点（Python，包 `odom_path_pkg`，文件 `odom_path_pkg/odom_path_node.py`）

```python
import math
import rclpy
from rclpy.node import Node
from nav_msgs.msg import Odometry, Path
from geometry_msgs.msg import PoseStamped


class OdomPathNode(Node):
    def __init__(self):
        super().__init__('odom_path_node')
        self.pub = self.create_publisher(Path, '/path', 10)
        self.sub = self.create_subscription(Odometry, '/odom', self.on_odom, 10)
        self.path = Path()
        self.path.header.frame_id = 'odom'
        self.min_dist = 0.05  # 米

    def on_odom(self, msg: Odometry):
        p = msg.pose.pose.position
        if self.path.poses:
            q = self.path.poses[-1].pose.position
            if math.dist((p.x, p.y), (q.x, q.y)) < self.min_dist:
                return
        ps = PoseStamped()
        ps.header = msg.header
        ps.pose = msg.pose.pose
        self.path.poses.append(ps)
        self.path.header.stamp = self.get_clock().now().to_msg()
        self.pub.publish(self.path)


def main():
    rclpy.init()
    rclpy.spin(OdomPathNode())
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

### 22.4.4 场景 4：单线激光雷达数据订阅与无效值过滤（C++ 片段，仿真/实机通用）

```cpp
#include "sensor_msgs/msg/laser_scan.hpp"

void onScan(const sensor_msgs::msg::LaserScan::SharedPtr msg) {
  for (size_t i = 0; i < msg->ranges.size(); ++i) {
    const float r = msg->ranges[i];
    if (!std::isfinite(r) || r < msg->range_min || r > msg->range_max) {
      continue;                       // inf/nan/越界点一律跳过
    }
    const float angle = msg->angle_min + i * msg->angle_increment;
    const float x = r * std::cos(angle);   // 极坐标 → 机器人坐标系
    const float y = r * std::sin(angle);
    (void)x; (void)y;                 // 后续可用于避障/建图
  }
}
```

### 22.5.4 传感器数据加工衔接（第3章 Canny+Otsu 实测回看）

虚拟传感器数据发布出去之后，接收端就是第3章那套 NumPy/OpenCV 加工工具箱：`sensor_msgs/Image` 经 `cv_bridge` 转 ndarray 后可直接走「高斯滤波 → Canny 边缘 → Otsu 阈值」流水线（第3章端到端实测，cv2 4.6.0 / numpy 1.26.4）：

```text
去均值后列均值: [0. 0. 0. 0.]
argmax: 11 median: 5.5
otsu threshold = 136.0 edges px = 1
blur shape: (200, 300) median dtype: uint8
```

合成带噪场景的完整闭环（合成 → 滤波 → 边缘/阈值 → 落盘 → 读回复核）实测：

```text
scene_raw.png: shape=(200, 300) mean=84.3
scene_edges.png: shape=(200, 300) mean=1.9
scene_binary.png: shape=(200, 300) mean=47.6
otsu=133/133 边缘像素=1
```

两次 Otsu 阈值一致（133）说明流水线确定性；边缘图均值 1.9 说明只有矩形轮廓处有响应。这套「数组加工」手法同样适用于本章的传感器数组：激光 `np.array(msg.ranges)` 过滤野值、`argmin` 找最近障碍，与 Canny+Otsu 是同一套 NumPy 范式（实测存档见第3章）。

## 22.6 与 ROS2 / 机器人开发的关联

1. **sensor_msgs 消息族的地基**：本章的 `LaserScan`、`PointCloud2` 与第23 章的 `Image`、`Imu`、`NavSatFix` 同属 `sensor_msgs`，字段设计哲学一致（header + 数据体 + 元信息）。吃透一个，其余接口阅读成本减半。
2. **tf2 坐标树的第一块拼图**：里程计案例产出的 `odom → base_link` 动态变换，加上激光雷达的 `base_link → laser_link` 静态变换，就是 SLAM（`map → odom`）与导航所需的完整 tf 链路的下半段。
3. **nav2 的输入契约**：Nav2 的 `controller_server` 依赖 `/odom`（或 EKF 融合后的 `/odometry/filtered`）做速度反馈，`costmap` 依赖 `/scan` 或 `/points` 做障碍层。消息组织不规范，Nav2 直接报「transform timeout」或代价地图全黑。
4. **仿真 → 实机迁移范式**：本章案例「先仿真跑通、再移植实体」的流程，会在第24 章（Ignition Gazebo）与第25 章（导航）反复复用；frame_id、话题名、QoS 三件套检查清单建议直接沉淀成脚本。

## 22.7 自测与练习

1. **概念题**：`nav_msgs/Odometry` 的 `header.frame_id` 与 `child_frame_id` 分别应该填什么？如果两者都填 `base_link`，tf2 会有什么表现？
2. **动手任务**：在本章 C++ 轨迹节点基础上增加一个「轨迹长度」字段（发布 `std_msgs/Float32` 或打印日志），要求：机器人绕仿真环境走一圈后，轨迹长度误差与真实周长之比 < 10%（用 rviz2 的 Measure 工具估算周长）。
3. **动手任务**：写一个节点订阅 `/scan`，实时发布「前方 30° 扇区内的最小距离」，并在 rviz2 中验证：靠近障碍物时数值应单调减小。

> 参考答案要点：1. `header.frame_id` 填 `odom`（位姿所在系），`child_frame_id` 填 `base_link`（被描述对象）；都填 `base_link` 会让 tf 树中 odom→base_link 缺失，rviz2 报 "No transform from [base_link] to [odom]"。2. 轨迹长度 = 相邻稀疏化后轨迹点欧氏距离累加；注意稀疏化阈值会造成正偏差，阈值越小越准。3. 最小距离 = 对 `ranges[i]` 中 `|angle| <= 15°` 且值有效的点取 min；务必过滤 `inf/nan`。

## 22.8 常见问题（FAQ）

- **Q：`ros2 node list` 在 PC 上看不到机器人节点？** A：按顺序排查：① 两端 `ROS_DOMAIN_ID` 是否一致；② 是否同一局域网/有无 AP 隔离；③ 防火墙是否放行 DDS 端口（7400 起的 UDP 段）；④ 多网卡机器可设 `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET` 或配置 FastDDS 单播。
- **Q：rviz2 中 Path 什么都不显示？** A：先查 `ros2 topic echo /path --once` 是否有数据；再查 rviz2 的 Fixed Frame 是否与 `Path.header.frame_id`（如 `odom`）在同一 tf 树；最后查 Path 显示项的 Topic 是否填对。
- **Q：`ranges` 里全是 `inf`？** A：说明该方向无回波（超出量程或吸光），属正常现象；若**全部**为 `inf`，查雷达供电、驱动话题名是否匹配、仿真插件的 `range_max` 是否配置过小。
- **Q：Python 版轨迹节点跑一会儿 rviz2 就卡？** A：`Path.poses` 无上限增长导致消息体积膨胀；按示例加稀疏化与上限，或改用 `nav_msgs/Path` 的环形缓冲策略。
- **Q：仿真里正常的 `/scan` 换到实机角度全反？** A：多为雷达安装方向与 URDF 中 `laser_link` 的 rpy 定义不一致；用 `ros2 run tf2_ros tf2_echo base_link laser_link` 核对静态变换，必要时在 URDF 中调整安装角或加 `yaw` 修正。

## 22.9 本章小结

- 里程计位姿 → Path 的关键是为每个 PoseStamped 填 `frame_id` 与 `stamp`，并做稀疏化与点数上限保护；
- 虚拟激光雷达按 `angle_min + i * angle_increment` 的角度语义合成 ±π 360 线扫描；虚拟点云用「宽高 + 字段 + 步长」组织 PointCloud2——虚拟传感器数据源让我们在**无硬件**条件下完成 SLAM/导航算法调试；
- C++ 的 PointCloud2Modifier 与 Python 的 point_cloud2 工具是构造点云的两个标准姿势；
- 传感器数组落回 NumPy/OpenCV（Canny+Otsu 流水线）即可做边缘、阈值类加工——虚拟数据源 + 通用加工工具箱 = 完整的离线算法调试环境。
