第15章 通信机制深度剖析

通信机制是 ROS2 的核心。本章依次完成话题、服务、动作、参数四种通信机制的案例实现（含自定义接口消息），每种机制都按「案例分析 → 接口消息 → C++ 实现 → Python 实现 → 运行效果」展开。

15.2 知识点梳理

15.2.1 第1课 通信机制简介和话题通信详解与实现

A. 通信机制简介

  • 节点与话题：节点（Node）是执行计算的进程单元；话题（Topic）是节点间异步单向广播的数据通道，一个话题可有多个发布方（Publisher）与多个订阅方（Subscriber），彼此不感知对方存在（发布订阅解耦）。节点间还能通过服务、动作、参数交互，统称 ROS2 通信机制。
  • 通信模型总览：ROS2 提供 4 种模型——话题（连续数据流）、服务（请求-响应）、动作（长任务 + 反馈 + 可取消）、参数（节点配置读写），底层都由 DDS 实现，但语义与 API 完全不同；运行时所有节点/话题/服务连成的拓扑称"计算图（Computation Graph）"，可用 rqt_graph 查看。
  • 接口（Interface）：数据类型由 .msg/.srv/.act 文件定义，经 rosidl 生成 C++/Python 类型；内置接口包有 std_msgs（基础类型）、geometry_msgs（几何）、sensor_msgs（传感器）、nav_msgs（导航）等；字段名小写下划线，常量全大写。
  • 准备工作：新建工作空间与功能包（--build-type ament_cmake 或 ament_python）；自定义接口时单独建接口功能包（只含 msg/ srv/ action/ 与 package.xml/CMakeLists.txt），其他包 depend 它——避免 rosidl 生成与节点编译耦合。

B. 话题通信详解与实现

  • 场景、概念、作用与消息接口：话题用于连续、单向、多对多的数据广播（激光雷达扫描数据、速度指令流等），概念上是"发布/订阅 + 消息队列（QoS 决定深度、可靠性、历史策略）"；消息接口即 .msg 文件，每行 类型 名称。
  • 案例以及案例分析：经典案例"学生话题"——发布方周期发布 std_msgs/String 或自定义 Student（姓名/年龄/身高），订阅方接收打印；分析要点：话题名、消息类型、发布频率、QoS 队列深度、发布/订阅各属哪个节点。
  • 原生消息 C++ 实现——发布方：三步——继承 rclcpp::Node 建类 → create_publisher<std_msgs::msg::String>("topic", 10) → create_wall_timer 周期回调里 publish；要点：成员保存 publisher、计数器自增、RCLCPP_INFO 打日志、回调避免长阻塞。
  • 原生消息 C++ 实现——订阅方：create_subscription<std_msgs::msg::String>("topic", 10, std::bind(&Class::cb, this, _1))；回调形参 std_msgs::msg::String::SharedPtr，只做轻量处理；要点：回调签名、队列深度与丢包语义、rclcpp::spin。
  • 原生消息 Python 实现——发布/订阅：self.create_publisher(String, 'topic', 10) + self.create_timer(0.5, cb)；订阅 self.create_subscription(String, 'topic', self.cb, 10)；注意 entry_points 注册与 destroy_node。
  • vscode 代码片段：把常用节点模板（类骨架、publisher/subscription、CMakeLists 模板）做成 vscode snippet（File > Preferences > Configure User Snippets），输入前缀自动展开，课程演示了 C++/Python 两套片段，可显著提速重复框架代码。
  • 自定义接口消息（接口文件）：接口包 msg/Student.msg 写 string name / int32 age / float64 height；package.xml 需 <buildtool_depend>rosidl_default_generators</buildtool_depend> + <member_of_group>rosidl_interface_packages</member_of_group>；CMakeLists.txt 需 rosidl_generate_interfaces(${PROJECT_NAME} "msg/Student.msg")；生成后用 ros2 interface show base_interfaces_demo/msg/Student 验证。
  • 自定义接口 C++ 实现：引用生成头文件 base_interfaces_demo/msg/student.hpp，类型写 base_interfaces_demo::msg::Student；CMakeLists.txt 增加 find_package(base_interfaces_demo REQUIRED) 与 ament_target_dependencies(... base_interfaces_demo)。常见坑：接口包没先编译、头文件路径错误。
  • 自定义接口 Python 实现：from base_interfaces_demo.msg import Student，用 msg.name = '张三' 赋值；Python 包 package.xml 加 <exec_depend>base_interfaces_demo</exec_depend>，setup.py 无需额外配置，但要 source 接口包的 install。
  • rqt 查看计算图：ros2 run rqt_graph rqt_graph 显示节点-话题拓扑，可快速验证"发布订阅是否连上、话题名是否一致"，配合 ros2 topic list/info/echo 排查。
  • 小结：话题 = 异步单向广播；接口可自定义；C++ 与 Python API 几乎一一对应；QoS 队列深度是最先要理解的参数。

15.2.2 第2课 服务通信详解与实现

  • 场景、概念与作用：服务（Service）是同步请求-响应模型：客户端（Client）发送请求（Request），服务端（Server）处理后返回响应（Response），一问一答、一次往返；适合"低频、需要结果"的场景：开关硬件、查询当前状态、切换模式。与话题的区别：话题是连续流、无人等待；服务是阻塞调用、有明确结果。
  • 案例以及案例分析：经典案例"求和/学生信息查询"——客户端发两个数（或学号），服务端返回和（或学生信息）；分析要点：定接口（请求字段/响应字段）、谁做服务端谁做客户端、客户端何时调用（定时器？收到话题后？）、超时与失败处理。
  • 自定义服务接口：srv/AddInts.srv 格式为 --- 之上是请求、之下是响应（int32 num1 / int32 num2 / --- / int32 sum）；生成配置与 .msg 相同（rosidl_generate_interfaces 中列出 .srv 文件）。
  • C++ 实现——框架与服务端：两个可执行文件（服务端 server、客户端 client）分别 add_executable + ament_target_dependencies；服务端 create_service<自定义srv>("服务名", std::bind(&cb, this, _1, _2))，回调签名 void cb(const Req::SharedPtr req, Resp::SharedPtr resp)，在回调里填 resp->sum——服务端是被动的，只有请求到来回调才触发。
  • C++ 实现——客户端（流程梳理）：三步——创建客户端 → 等待服务可用（wait_for_service）→ 发送请求并等待响应（async_send_request + spin_until_future_complete）。
  • C++ 实现——连接服务 BUG 说明：常见 BUG 是"服务端还没起来客户端就退出"或"用 spin 等待导致死锁"。正确姿势：wait_for_service 带超时 + 判断返回值；异步请求后用 rclcpp::spin_until_future_complete(node, future) 而不是再 spin；注意客户端节点与回调组（CallbackGroup）在多线程执行器下的互斥问题。
  • C++ 实现——发送请求处理响应：填 request->num1/num2，auto future = client->async_send_request(request)；spin_until_future_complete 返回后 future.get() 取响应并打印；处理超时（future.wait_for）与失败分支。
  • Python 实现——服务端/客户端：服务端 self.create_service(AddInts, 'add_ints', self.cb)，回调 (req, resp) 填 resp 并返回；客户端 self.create_client(AddInts, 'add_ints')、cli.wait_for_service()、future = cli.call_async(req)、rclpy.spin_until_future_complete(node, future)、future.result()。
  • 小结：服务 = 同步一问一答；.srv 接口请求/响应用 --- 分隔；客户端必须处理"服务未就绪/超时"；阻塞调用不适合长时间任务（那是动作的活）。

15.2.3 第3课 动作通信详解与实现

  • 场景、概念与作用：动作（Action）= 服务 + 话题反馈 + 取消 + 结果，面向耗时长、需要进度反馈、可能中途取消的任务：导航到目标点、机械臂规划执行、相机长曝光。结构是"目标（Goal）→ 连续反馈（Feedback）→ 最终结果（Result）"三段式，底层由两个话题 + 一个服务组合而成。
  • 案例以及案例分析：经典案例"累加求和/乌龟走目标点"——客户端发目标（数字 n/坐标），服务端周期反馈进度（百分比/已完成量），支持取消，最后返回成功与否；分析要点：Goal/Feedback/Result 字段、执行频率、取消语义。
  • 自定义动作接口：action/Progress.action 三段用 --- 分隔（课程约定：目标段 / 结果段 / 反馈段，如 int64 num / --- / int64 sum / --- / float64 progress）；生成配置与 .msg/.srv 相同，用 ros2 interface show base_interfaces_demo/action/Progress 验证。
  • C++ 实现——服务端三回调：rclcpp_action::create_server<NodeT>(node, "动作名", handle_goal, handle_cancel, handle_accepted)——handle_goal 检查目标合法性（如 num >= 1）返回 rclcpp_action::GoalResponse::ACCEPT_AND_EXECUTE 或 REJECT（非法目标如越界/NaN 必须在此拒绝，避免执行线程崩溃）；handle_cancel 返回 ACCEPT/REJECT；handle_accepted 取 GoalHandle 启动执行线程跑主逻辑。
  • C++ 实现——主逻辑与取消处理：执行循环里推进状态：计算中间量 → publish_feedback 反馈进度 → rclcpp::Rate 控制频率 → 到达目标后 goal_handle->succeed(result)；每周期检查 goal_handle->is_canceling()，为真则填 result、goal_handle->canceled(result) 返回并退出线程。
  • C++ 实现——bug 修复：典型问题——执行线程生命周期（detach 的线程访问已销毁节点）、回调组未设 Reentrant 导致取消回调被阻塞、忘记判断 is_canceling、反馈频率过高阻塞执行器；修复：互斥锁保护共享状态、正确设置回调组、Rate 控频。
  • C++ 实现——客户端与三类响应：rclcpp_action::create_client<ActionT>(node, "动作名") → async_send_goal（带目标选项，注册 feedback/result 回调）→ spin_until_future_complete → goal_handle；async_get_result 等结果；取消用 async_cancel_goal。目标响应确认"被接受了吗"；反馈回调收 FeedbackMessage；最终响应取 WrappedResult 的 code（SUCCEEDED/CANCELED/ABORTED）与 result。
  • Python 实现——服务端/客户端：服务端 rclpy.action.ActionServer(self, Progress, 'get_sum', self.execute_callback, goal_callback=..., cancel_callback=...)，execute_callback(goal_handle) 里循环反馈，最后 goal_handle.succeed() 并 return result；客户端 ActionClient → send_goal_async(goal, feedback_callback=fb) → spin_until_future_complete → get_result_async 取结果，cancel_goal_async 取消。
  • 小结：动作适合长任务；服务端三回调（goal/cancel/accepted）+ 主循环；客户端四步（建、连、发、收）；务必处理取消与异常退出。

15.2.4 第4课 参数服务详解与实现

  • 场景、概念与作用：参数（Parameter）是节点内的键值配置，运行期可读写（含 ros2 param set 热改），用于 PID 增益、话题名、算法开关、限速值等。每个节点自带参数服务端，ros2 param 命令与 rqt_reconfigure 即参数客户端。
  • 案例以及案例分析：服务端节点声明 car_name=tiger（string）、width=1.55（double）、wheels=5（int），演示增→查→改→查→删→查全流程；客户端节点远程读写服务端参数。分析要点：哪些量做成参数、默认值、类型、改动后是否需要回调生效。
  • 参数简介：参数类型限定 6 种——bool、int64、double、string、byte_array、bool/int64/double/string 数组；参数名 = 节点名 + 参数名（如 /node/param）；生命周期：声明（declare）→ 读（get）→ 改（set，可触发回调）→ 可 undeclare。
  • 参数简介——C++ API：declare_parameter("k", 1.0)、get_parameter("k").as_double()、set_parameter(rclcpp::Parameter("k", 2.0))、add_on_set_parameters_callback 监听修改做合法性校验。
  • 参数简介——Python API：self.declare_parameter('k', 1.0)、self.get_parameter('k').value、self.set_parameters([Parameter('k', Parameter.Type.DOUBLE, 2.0)])、self.add_on_set_parameters_callback(cb)。
  • C++ 实现——服务端（增查改删）：增——declare_parameter（动态参数写法见 15.4.5 兼容提示）；查——get_parameter/list_parameters/describe_parameters；改——set_parameter（触发回调）；删——undeclare_parameter。要点：声明时给默认值避免 NOT_DECLARED 异常。
  • C++ 实现——客户端（查/改）：用参数客户端类 rclcpp::AsyncParametersClient（底层即 rcl_interfaces::srv::GetParameters/SetParameters 服务）——get_parameters/set_parameters 异步获取 future；spin_until_future_complete 取值；也可直接命令行 ros2 param list/get/set/dump。
  • Python 实现——服务端（增查改删）：declare_parameter（增）、get_parameter（查）、set_parameters（改）、undeclare_parameter（删）；list_parameters 列出全部；add_on_set_parameters_callback 回调里做范围校验（如颜色 0-255）。
  • 小结：参数是节点配置层，不是数据通信层；适合低频、小数据、需要热改的场景；所有参数操作本质都是对节点内参数服务的调用。

15.2.5 四种通信模型横向对比（本章总结）

维度 话题（Topic） 服务（Service） 动作（Action） 参数（Parameter）
交互模式 发布/订阅，单向广播 请求/响应，一问一答 目标→反馈→结果 键值读写
同步性 异步，发布不等订阅 同步阻塞（客户端等响应） 异步（回调/状态机） 同步调用（底层是服务）
数据流向 1→N，双向靠两个话题 1→1 往返 1→1 + 持续反馈流 客户端↔节点参数服务
时长语义 持续流 短暂（毫秒级） 长任务（秒~分钟） 瞬时
可取消 不适用 不支持 支持 不适用
适用场景 传感器数据、速度指令、状态广播 查询状态、开关、一次性变换 导航、抓取、长时运动 配置、PID 参数、开关量
QoS 影响 关键：可靠性/历史/深度/截止期直接决定丢包与延迟 QoS 由服务底层话题决定，通常可靠 目标/反馈/结果走内置话题，QoS 固定策略 内置服务，可靠调用
典型失败 QoS 不匹配（BEST_EFFORT vs RELIABLE）、队列溢出 服务端未启动、阻塞死锁 取消未处理、执行线程泄漏 未声明就 get、类型不符

注意： 选型口诀——连续数据用话题、要结果的短调用用服务、长任务用动作、配置项用参数。QoS 不匹配是话题通信最常见的"看起来连上了就是没数据"原因，用 ros2 topic info -v 查看两端 QoS。

15.3 重点与难点

  1. 自定义接口包的独立性：接口必须放在独立功能包，rosidl_generate_interfaces + <member_of_group>rosidl_interface_packages</member_of_group> 缺一不可；下游包 find_package 后才能用生成的 C++/Python 类型。
  2. 服务客户端的时序：服务端未就绪时 async_send_request 会失败或挂起；必须 wait_for_service + spin_until_future_complete，并处理超时（课程专门讲了连接 BUG）。
  3. 动作服务端的三回调 + 主循环：goal（准入校验）、cancel（接受取消）、accepted（起执行体）分工不能乱；执行循环必须检查 is_canceling()，否则取消请求会被忽略。
  4. 参数的声明语义：ROS2 参数"先声明后使用"，get 未声明参数会抛异常；set 触发的回调里要返回 SetParametersResult，用它做范围校验。
  5. 四种模型的选择：见 15.2.5 对比表；误用（如用服务传传感器流、用话题做长任务控制）会导致阻塞、丢数据或无法取消。

服务端（cpp02_service/src/demo01_server.cpp）：

using AddInts = base_interfaces_demo::srv::AddInts;
using namespace std::placeholders;

class AddIntsServer: public rclcpp::Node{
public:
    AddIntsServer():Node("add_ints_server_node_cpp"){
        RCLCPP_INFO(this->get_logger(),"服务端节点创建!");
        // 3-1.创建服务端；
        server_ = this->create_service<AddInts>("add_ints",std::bind(&AddIntsServer::add,this,_1,_2));

private:

客户端（demo02_client.cpp）通过命令行参数提交数据，spin_until_future_complete 等待响应。规避"服务未就绪"BUG 的标准写法（笔记版示例）：

// add_client/src/client.cpp
#include "rclcpp/rclcpp.hpp"
#include "base_interfaces_demo/srv/add_ints.hpp"

int main(int argc, char ** argv) {
  rclcpp::init(argc, argv);
  auto node = rclcpp::Node::make_shared("add_client");
  auto client = node->create_client<base_interfaces_demo::srv::AddInts>("add_ints");
  while (!client->wait_for_service(std::chrono::seconds(1))) {   // 关键：等待服务上线
    if (!rclcpp::ok()) return 1;
    RCLCPP_INFO(node->get_logger(), "waiting for service...");
  }
  auto req = std::make_shared<base_interfaces_demo::srv::AddInts::Request>();
  req->num1 = 3; req->num2 = 5;
  auto future = client->async_send_request(req);
  if (rclcpp::spin_until_future_complete(node, future) == rclcpp::FutureReturnCode::SUCCESS) {
    RCLCPP_INFO(node->get_logger(), "sum = %ld", future.get()->sum);
  } else {
    RCLCPP_ERROR(node->get_logger(), "service call failed");
  }
  rclcpp::shutdown();
  return 0;
}

15.4.4 动作（Progress）：接口与实现要点

需求：客户端提交一个整型数 n，服务端连续反馈求和进度（百分比），最终响应 1~n 的累加和。接口 action/Progress.action：

服务端（cpp03_action/src/demo01_action_server.cpp）要点：目标处理 num >= 1 才接受（ACCEPT_AND_EXECUTE），否则拒绝；执行体在子线程中运行（std::thread{...}.detach()），以 Rate(1Hz) 连续反馈 progress；执行体骨架为 while + is_canceling() + publish_feedback + Rate + succeed/canceled（取消时填结果并 canceled(result) 退出，完成后 succeed(result) 提交累加和）；客户端（demo02_action_client.cpp）注册目标响应/连续反馈/最终响应三个回调。

# param_demo/param_demo/param_node.py
import rclpy
from rclpy.node import Node
from rcl_interfaces.msg import SetParametersResult


class ParamNode(Node):
    def __init__(self):
        super().__init__('param_node')
        self.declare_parameter('bg_r', 255)          # 增：声明 + 默认值
        self.add_on_set_parameters_callback(self.on_set)

    def on_set(self, params):
        for p in params:
            if p.name == 'bg_r' and not (0 <= p.value <= 255):   # 改：合法性校验
                return SetParametersResult(successful=False, reason='0~255 only')
        return SetParametersResult(successful=True)

15.6 与 ROS2 / 机器人开发的关联

  1. 传感器与控制全靠话题：激光雷达 /scan、相机 /image_raw、里程计 /odom、速度指令 /cmd_vel 全是话题；掌握 QoS 与队列语义才能写对订阅端。
  2. 导航与机械臂靠动作：Nav2 的 NavigateToPose、MoveIt2 的 execute_trajectory 都是动作接口；本章的三回调模型直接复用到工业项目。
  3. 服务用于系统管理：定位模式切换、保存地图（/map_saver）、硬件开关；参数用于在线调参（PID、限速），rqt_reconfigure 就是参数客户端 GUI。
  4. 自定义接口是团队协作契约：真实项目中接口包由系统架构师统一定义，各小组按接口开发再联调——本章训练的 .msg/.srv/.act 流程就是这份契约的落地方式。

15.8 常见问题（FAQ）

  • Q：订阅了话题却收不到数据？ A：按序排查——节点是否在跑（ros2 node list）、话题名是否完全一致（含命名空间）、消息类型是否一致（ros2 topic info）、QoS 是否匹配（ros2 topic info -v，可靠发布 + 尽力订阅不兼容是常见原因）、ros2 topic echo 确认有数据。
  • Q：服务客户端卡住不动？ A：多半是没 wait_for_service 或用错 spin 方式；也可能是服务端回调阻塞了执行器。用 ros2 service list 确认服务存在，ros2 service call 手动验证服务端。
  • Q：动作取消没反应？ A：检查服务端执行循环是否轮询 is_canceling()、取消回调是否返回 ACCEPT、执行体是否跑在会阻塞执行器的线程里。
  • Q：ros2 param set 报 "Parameter not declared"？ A：ROS2 要求参数先声明；在节点构造函数里 declare_parameter（带默认值）。另外参数名大小写敏感。
  • Q：自定义接口改了字段，编译没生效？ A：接口包要重新 colcon build（rosidl 重新生成），下游包也要重编；极端情况删 build/ install/ 重新编译。
