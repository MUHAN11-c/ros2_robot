23.2 知识点梳理

23.2.1 第1课 传感器之相机和IMU详解与仿真案例（3h15m · 26 节）

  • 核心概念：相机（Camera）把三维世界投影为二维图像，提供颜色/纹理/语义信息；IMU（Inertial Measurement Unit，惯性测量单元）测量自身角速度与线加速度，提供高频的姿态与运动信息。二者常与雷达/里程计互补使用。
  • 要点 1 · 相机概念、作用与特点：作用是目标识别、视觉 SLAM、远程监控；特点是信息量大（数据率高）、受光照影响、无直接深度（单目）、计算开销大。

  • 要点 2 · 相机分类：

    | 类型 | 代表 | 输出 | 典型用途 | |---|---|---|---| | 单目（Monocular） | USB 摄像头 | Image | 视觉识别、监控 | | 双目（Stereo） | ZED、小觅 | 左右 Image + 视差/深度 | 稠密深度估计 | | 深度（Depth / RGB-D） | RealSense、Kinect、奥比中光 | Image + PointCloud2 + CameraInfo | 避障、三维重建 | | 其他 | 鱼眼、全景、红外 | Image | 特殊场景 |

  • 要点 3 · 单目相机使用：硬件准备（USB 相机 + 权限：加入 video 组）、软件安装（sudo apt install ros-humble-usb-cam）；usb_cam 功能包发布 /image_raw（sensor_msgs/Image）与 /camera_info（sensor_msgs/CameraInfo）；自定义功能包封装驱动时注意：用 image_transport 而非裸 Publisher<Image>，才能获得压缩图传能力。

  • 要点 4 · 深度相机使用：除 RGB 图外输出对齐深度图与 PointCloud2；使用要点是配准（depth 与 color 对齐）、深度有效范围（如 0.3–5 m）、以及 CameraInfo 中内参的一致性。

  • 要点 5 · Image 消息接口：header + height/width + encoding（rgb8/bgr8/mono8/16UC1 等）+ is_bigendian + step（每行字节数）+ data[]（行优先裸字节）。

    注意： encoding 决定 data 的解析方式，bgr8 与 rgb8 通道顺序相反；OpenCV 的 cv::Mat 默认 BGR，与 rgb8 话题混用会出现「蓝蓝的图像」。

  • 要点 6 · 单目相机仿真案例（C++ 三讲 + Python 三讲）：在仿真中发布一幅自造图像，流程与雷达案例同构：案例分析（组织 Image 消息）→ 框架搭建（定时器 + 发布者）→ 组织图片基本参数（height/width/encoding/step）→ 填充 data 并发布 → 测试与小结。

  • 要点 7 · IMU 概念与接口：优点是高频（100–1000 Hz）、不受外界环境干扰、短期精度高；缺点是积分漂移（加速度二次积分误差随时间平方增长）、需要标定与温漂补偿。sensor_msgs/Imu 字段：orientation（四元数，来自姿态解算/磁力计融合）、angular_velocity（rad/s）、linear_acceleration（m/s²）及三者 3×3 协方差；无输出能力的轴用协方差 [0] = -1 标记。
  • 要点 8 · IMU 案例（C++ 两讲 + Python 一讲）：订阅 /imu，解算并发布姿态可视化（如把 orientation 转欧拉角发布、或驱动 rviz2 中一个姿态箭头），理解四元数 → 欧拉角换算与 tf2 中 getYaw 的用法。

23.2.2 第2课 GNSS详解与轮式里程计标定与融合（3h57m · 33 节）

  • 核心概念：GNSS（Global Navigation Satellite System，全球导航卫星系统，含 GPS/北斗/GLONASS/Galileo）提供绝对经纬度与海拔；轮式里程计标定（Odometry Calibration）是用实测修正轮径/轮距参数，让里程计推算逼近真实运动。
  • 要点 1 · GNSS 特点与分类：提供绝对位置、无累积漂移，但更新率低（1–10 Hz）、精度受环境影响（城市峡谷、遮挡）、输出经纬度需投影到平面坐标；分类按精度：单点定位（米级）、差分 DGNSS/RTK（厘米级）。
  • 要点 2 · GNSS 基本使用与消息接口：sensor_msgs/NavSatFix：latitude/longitude（度）/altitude（m）、status（STATUS_NO_FIX/STATUS_FIX/STATUS_SBAS_FIX/STATUS_GBAS_FIX，含 service 位标志）、position_covariance（3×3，单位 m²）与 position_covariance_type。配套 sensor_msgs/NavSatStatus、sensor_msgs/TimeReference。
  • 要点 3 · GNSS 案例（C++ 六讲 + Python 三讲）：需求是「把 GNSS 历史定位点组织成可视化轨迹」，难点全在坐标系与投影： ① 框架搭建 → ② Path 数据组织标头（header.frame_id 常用 map 或 gps）→ ③ 坐标系确定 → ④ 原点确定（首帧经纬度作为局部 ENU 原点）→ ⑤ 经纬度转平面坐标（等距圆柱近似：x = (lon - lon0)·cos(lat0)·111320，y = (lat - lat0)·110540；工程上更推荐 robot_localization/navsat_transform_node 或 GeographicLib 的 UTM 投影）→ ⑥ 数据组织完成与小结。
  • 要点 4 · 轮式里程计标定：场景是里程计推算位姿与真实位姿存在系统性偏差；流程分两步——线性位移标定（让机器人直行标称距离如 10 m，实测偏差用于修正轮径系数 scale_x）与角速度标定（让机器人原地旋转标称角度如 360°，实测偏差用于修正轮距 wheel_separation）。标定实现即写脚本发布 /cmd_vel、订阅 /odom 统计累计位移/转角、输出修正系数。

  • 要点 5 · 轮式里程计与 IMU 融合（robot_localization）：

    | 步骤 | 内容 | |---|---| | 1 简介安装 | sudo apt install ros-humble-robot-localization | | 2 包简介 | 提供 ekf_node（扩展卡尔曼滤波 EKF）与 ukf_node，支持多输入源融合 | | 3 融合准备 | 明确各传感器坐标系、话题、QoS；准备 EKF 参数 yaml | | 4 launch 框架 | 一个 launch 集成底盘驱动、IMU 静态变换、EKF 节点 | | 5 底盘实现 | 底盘节点发布 /odom（轮速积分）与 odom → base_link tf | | 6 IMU 坐标变换 | static_transform_publisher 或 URDF 定义 base_link → imu_link | | 7 EKF 融合 | ekf_node 订阅 /odom + /imu，发布 /odometry/filtered 与 odom → base_link（EKF 版） | | 8 执行验证 | rviz2 对比 /odom 与 /odometry/filtered 轨迹，融合后应更平滑、漂移更小 |

  • EKF 关键配置思想：每个传感器输入用 odom0/imu0 系列参数声明，布尔数组 odom0_config 指定融合哪些状态量（如 IMU 只融合 yaw 角速度与加速度、不融合其绝对姿态），并处理好「谁发布 odom → base_link」的唯一性（开启 EKF 的 publish_tf 后，底盘端要关掉自己的 tf 发布）。

23.2.3 第3课 激光雷达工具和相机使用进阶（4h01m · 31 节）

  • 核心概念：原始传感器数据要经过「过滤 → 融合 → 格式转换」的加工流水线才能喂给 SLAM/导航；相机进阶则解决远程传输、标定精度与多相机扩展。
  • 要点 1 · 雷达过滤器（laser_filters）：功能包提供 scan_to_scan_filter_chain 节点，通过插件链（plugin chain）加工 /scan：LaserScanRangeFilter（裁剪量程外数据）、LaserScanAngularBoundsFilter（裁剪角度扇区，如屏蔽机器人自身结构遮挡）、LaserScanSpeckleFilter（滤孤立噪点/飞点）、LaserScanShadowsFilter（滤阴影伪影）。应用案例：① 过滤无效数据（inf/nan → 报错阈值剔除）；② 设置有效范围（仅保留 0.15–8 m，避免自遮挡回波）。
  • 要点 2 · 雷达融合（ira_laser_tools）：场景是单雷达视野受限、需多雷达拼接 360°。laserscan_multi_merger 节点按各雷达的 tf 把多路 /scan 融合为一路。案例五步：需求分析 → 雷达端口重映射（两台雷达 USB 端口号会漂移，用 udev 规则或 launch remap 固定话题）→ 启动两个雷达 → 坐标系集成（为两雷达分别建 laser_front_link/laser_rear_link 静态 tf，并统一到 base_link）→ 融合实现（配置 destination_frame、cloud_destination_topic/scan_destination_topic）。扩展案例：融合后再过滤（merger 输出接 scan_to_scan_filter_chain）。

  • 要点 3 · 点云与激光扫描互转：

    | 方向 | 工具 | 典型用途 | |---|---|---| | LaserScan → PointCloud2 | laser_geometry::LaserProjection（C++ API） | 2D 雷达数据并入三维处理管线、多传感器同视图显示 | | PointCloud2 → LaserScan | pointcloud_to_laserscan 节点 | 3D 雷达/深度相机「压扁」成 2D 扫描，喂给 2D SLAM 与导航 |

    转换时要指定 target_frame、高度裁剪区间（min_height/max_height，只取地面以上 0.1–1.0 m 的点做避障）与角度范围。

  • 要点 4 · 相机进阶 · 远程图传：机器人端跑相机节点、PC 端看图，原始图带宽大（640×480×3×30 ≈ 27 MB/s），需压缩：用 image_transport 的 compressed 传输插件发布 /image_raw/compressed，PC 端解压显示（image_transport 自动订阅压缩话题，或用 rqt_image_view）。本地解压缩两讲即讲解 CompressedImage 与 cv_bridge 解码。

  • 要点 5 · 相机进阶 · 标定：标定（Calibration）是求解内参（焦距 fx/fy、主点 cx/cy、畸变系数）与外参的过程。流程：打印棋盘格标定板 → ros2 run camera_calibration cameracalibrator --size 8x6 --square 0.024 image:=/image_raw camera:=/camera → 移动标定板采集多角度样本 → 得到 camera_info（YAML）→ 使用标定参数（发布 /camera_info、图像去畸变 image_proc）。
  • 要点 6 · 相机进阶 · 多相机：多路 USB 相机设备号（/dev/video0/2/...）开机后会随机漂移，端口绑定用 udev 规则（按 USB 物理端口序列号固定 video* 别名）；再按需求添加前相机、后相机（各自命名空间 /front_camera、/rear_camera，独立 CameraInfo 与 tf 链杆）。

23.3 重点与难点

  1. Image 的 encoding 与内存布局：step = width × 每像素字节数（可能含行对齐 padding），data.size() = step × height。用 cv_bridge 转 cv::Mat 时选错编码会得到色彩错乱或直接异常。
  2. GNSS 的坐标投影：经纬度不能直接当平面坐标用。统一做法：以首帧为原点做 ENU 投影（或交给 navsat_transform_node），并声明 frame_id；忘了投影，轨迹在 rviz2 中只是一个「远处的小点」。
  3. IMU 漂移与协方差：IMU 短期准、长期漂。EKF 融合时必须为各传感器配置合理的协方差（不确定度），否则「谁嗓门大听谁的」，融合结果反而更差。
  4. 多雷达融合的坐标系前提：merger 依赖 tf 把各路扫描变换到 destination_frame；tf 缺失或时间戳不同步时，融合结果是「错位的拼图」。先 tf2_echo 验证每路雷达的静态变换再启动融合。
  5. 里程计标定的实验设计：直行距离要长（≥5 m）、旋转圈数要多（≥2 圈）、地面摩擦一致、电池电压稳定；单次实验误差大，取 3–5 次平均。
  6. 仿真 → 实机迁移要点：仿真中传感器无噪声、时间戳完美；实机上要考虑驱动延迟、时钟同步（use_sim_time 切换）、丢帧与抖动，代码里时间相关逻辑一律用消息自带的 header.stamp 而不是 now()。

23.4.4 场景 4：IMU 订阅与欧拉角解算（rclpy，文件 imu_monitor.py）

import math
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import Imu
from tf_transformations import euler_from_quaternion   # 或手动换算


class ImuMonitor(Node):
    def __init__(self):
        super().__init__('imu_monitor')
        self.create_subscription(Imu, '/imu', self.on_imu, 50)  # IMU 高频，QoS 放宽

    def on_imu(self, msg: Imu):
        q = msg.orientation
        roll, pitch, yaw = euler_from_quaternion([q.x, q.y, q.z, q.w])
        gz = msg.linear_acceleration.z                     # 静止时应约等于 9.8
        self.get_logger().info(
            f'yaw={math.degrees(yaw):.1f}deg  az={gz:.2f}m/s^2',
            throttle_duration_sec=1.0)                     # 限频打印


def main():
    rclpy.init()
    rclpy.spin(ImuMonitor())
    rclpy.shutdown()

23.6 与 ROS2 / 机器人开发的关联

  1. sensor_msgs 消息族全景成型：本章补全 Image/CameraInfo、Imu、NavSatFix，与上一章 LaserScan/PointCloud2 共同构成机器人感知接口层；header.frame_id + header.stamp 是它们接入 tf2 与消息滤波器（message_filters 时间同步）的钥匙。
  2. tf2 坐标树的传感器挂载：每类传感器都需要 base_link → <sensor_link> 的静态变换（URDF 或 static_transform_publisher）；EKF 融合后还要理清谁发布 odom → base_link，这是导航场景 tf 冲突的头号来源。
  3. nav2 的输入质量决定导航质量：Nav2 的代价地图（costmap）用 /scan 或 /points，AMCL 用 /scan + /odom，controller_server 用融合里程计。本章的过滤/融合/标定直接决定导航是否抖动、是否撞障。
  4. robot_localization 是导航前的必修课：EKF 输出的 /odometry/filtered 建议作为 Nav2 的标准里程计输入；对 GNSS 机器人，navsat_transform_node + 双 EKF 是室外导航的标配架构。
  5. 仿真 → 实机迁移：标定参数（轮径、轮距、相机内参、IMU 零偏）是纯「实机量」，仿真里永远拿不到；建立标定流程意识，比记住某个系数更重要。

23.7 自测与练习

  1. 概念题：sensor_msgs/Image 的 encoding 为 bgr8 时，data 中每个像素的三个字节分别是什么通道？与 rgb8 相比，直接用 numpy 按 rgb 显示会怎样？
  2. 动手任务：搭建双雷达融合环境（仿真中用两个 laserscan 插件分别朝前、朝后），经 laserscan_multi_merger 输出 360° 融合扫描。验收标准：rviz2 中两个雷达的障碍物点云无缝拼接，tf2_echo base_link laser_front_link 有稳定输出。
  3. 动手任务：完成轮式里程计线性标定：命令机器人直行 5 m（仿真或实机），记录 /odom 推算距离，计算修正系数并应用，复测 3 次误差 < 5%。

参考答案要点：1. bgr8 每像素依次为蓝、绿、红通道；按 rgb 解释会蓝红互换（天空变红）。2. 融合前必须有 base_link → laser_*_link 静态 tf 且两路 scan 时间戳有效；无缝拼接的关键是安装角与 tf 精确。3. 修正系数 = 目标距离 / 实测里程计距离，乘到底盘的轮径参数上；多次实验取平均以抑制地面打滑误差。

23.8 常见问题（FAQ）

  • Q：/image_raw 能收到但显示花屏？ A：多为 encoding 与实际数据不符（如相机输出 YUYV 却声明 rgb8），或 step 计算错误（忽略行对齐）；用 ros2 topic echo /image_raw --field encoding 核对，usb_cam 中显式设置 pixel_format。
  • Q：EKF 启动后 tf 报 odom → base_link 冲突/跳变？ A：底盘驱动与 ekf_node 同时发布了同一变换。二选一：底盘只发 /odom 话题不发 tf，由 EKF publish_tf: true 统一发布。
  • Q：GNSS 轨迹在 rviz2 中是个点？ A：经纬度未投影，数值量级（116°、39°）远超地图尺度。按首帧做 ENU 投影或使用 navsat_transform_node。
  • Q：多相机时 /dev/video* 顺序随机？ A：设备号按枚举顺序分配，插拔后会变。写 udev 规则按 USB 端口序列号固定符号链接（如 /dev/camera_front），launch 中用符号链接启动。
  • Q：雷达融合后 rviz2 中两圈扫描错位？ A：检查各雷达静态 tf 的平移/旋转是否与实际安装一致、destination_frame 是否为共同祖先（base_link）、两雷达驱动的系统时间是否同步（NTP/chrony）。

23.9 本章小结

  • 相机/IMU/GNSS 的消息规范（Image/Imu/NavSatFix）是接入真实驱动前最好的「接口演练」：编码决定字节序、四元数携带姿态、经纬度必须投影；
  • GNSS → 平面坐标的转换是导航模块（如 robot_localization）内部的必备步骤；
  • IMU 短期准、长期漂，EKF 融合要靠协方差与「谁发 tf」的唯一性约束兜底；
  • 雷达工具链（过滤/融合/互转）与相机进阶（图传/标定/多相机）把原始数据加工成 SLAM 与导航可直接消费的状态。
