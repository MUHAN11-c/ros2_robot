## 21.2 知识点梳理

### 21.2.1 第1课 树莓派及 Lifecycle 状态机开发

**核心概念**：colcon（common build tool）是 ROS2 的官方构建工具，负责工作空间中多包的增量编译、依赖排序与测试；生命周期节点把节点运行过程显式建模为状态机；两者合起来解决「多包工程如何部署到树莓派」与「硬件驱动如何安全启停」两个问题。

**要点 1：colcon 概念、功能与优势**。与 catkin 不同，colcon 与构建系统解耦（支持 ament_cmake / cmake / setuptools），自动拓扑排序并行构建、支持增量编译与 symlink-install，内建测试与结果汇总，是跨平台（x86 / ARM / Windows）一致的构建入口。

**要点 2：colcon 指令族**：

| 指令 | 作用 | 常用参数 |
|---|---|---|
| `colcon build` | 构建工作空间 | `--packages-select`、`--symlink-install`、`--parallel-workers`、`--cmake-args` |
| `colcon info <pkg>` | 查看包的元信息与依赖 | `--packages-up-to` 联用定位构建集 |
| `colcon list` | 列出工作空间所有包 | `--paths-only` 仅输出路径 |
| `colcon test` | 运行测试并汇总结果 | 配合 `colcon test-result --verbose` |
| `colcon graph` | 绘制包依赖关系图 | `--packages-up-to` / `--packages-deps` |

**要点 3：Windows 安装 ROS2 系列**。效果演示与安装说明之后，按序完成 choco（包管理）→ Python → VC++ 运行时环境 → OpenSSL → Visual Studio → OpenCV → 依赖安装 → Qt5 → RQT，再安装 ROS2 并测试，最后总结与拓展。这套「先装包管理器与编译工具链、再装依赖库、最后装 ROS2 并跑 demo 验证」的顺序，同样适用于树莓派（Ubuntu arm64 用 apt 替代 choco；资源紧张时选 `ros-humble-ros-base` 而非桌面全量版）。

**要点 4：树莓派部署要点**。x86 开发机上 `colcon build` 调通后，同步源码到板端本机编译（或用交叉编译工具链）；限制并行编译数防 OOM；用 `ROS_DOMAIN_ID` 划分多机域、`RMW_IMPLEMENTATION` 统一中间件；用 `top`/`free` 观察内存，必要时加 swap；`--symlink-install` 便于板上改参数即生效。

**要点 5：生命周期（Lifecycle）概念与应用场景**。普通节点启动即全速工作，而机器人硬件（雷达、电机、机械臂）需要「先配置、再激活、可暂停、可回收」的受控流程。生命周期节点把这一流程标准化，常用于硬件驱动、SLAM、导航栈这类启动昂贵或危险的节点。

**要点 6：状态机 4 状态与 6 回调**。主状态为 Unconfigured / Inactive / Active / Finalized，迁移由 `on_configure`、`on_activate`、`on_deactivate`、`on_cleanup`、`on_shutdown`、`on_error` 六个回调实现，任一回调返回 FAILURE 即进入错误处理流程：

| 迁移 | 触发命令 | 回调 | 典型动作 |
|---|---|---|---|
| Unconfigured → Inactive | `ros2 lifecycle set <node> configure` | `on_configure` | 创建话题/服务、打开设备句柄 |
| Inactive → Active | `activate` | `on_activate` | 启动定时器、开始发布、上电使能 |
| Active → Inactive | `deactivate` | `on_deactivate` | 停止采集、下电，保留资源 |
| Inactive → Unconfigured | `cleanup` | `on_cleanup` | 释放资源，回到初始 |
| 任意 → Finalized | `shutdown` | `on_shutdown` | 最终清理 |
| 回调返回 FAILURE | — | `on_error` | 尝试恢复或放弃 |

**要点 7：C++ 实现（框架 → 函数实现 → 执行）**。继承 `rclcpp_lifecycle::LifecycleNode`，覆写六个 `CallbackReturn` 回调；发布者用 `rclcpp_lifecycle::LifecyclePublisher`，只有 Active 状态才真正发出消息；主函数无需特殊处理，照常 `spin` 即可。

**要点 8：Python 实现（框架上/下 → 函数实现 → 执行）**。rclpy 对应 `LifecycleNode`（`rclpy_lifecycle`），回调签名与 C++ 一致；课程用同一案例双语言实现，便于对比 API 差异，小结强调状态机带来的可管理性。

### 21.2.2 第2课 进程内通信、话题管理与参数事件处理

**核心概念**：默认情况下即使发布、订阅在同一进程内，数据也要走序列化与共享内存；进程内通信（Intra-Process Communication）让同进程节点间以指针移交代替拷贝。话题统计与内容过滤提供运行时可观测性与带宽裁剪，参数事件让参数变化成为可订阅的事件流。

**要点 1：进程内通信场景、概念与作用**。把感知、规划多个节点装进同一进程（组件容器）时，大消息（图像、点云）的序列化开销会显著抬高延迟；开启进程内通信后，`unique_ptr` 发布实现「零拷贝」，订阅侧以 `ConstSharedPtr` 读取，中间件仅做指针移交与生命周期计数。

**要点 2：实现要点（C++）**。`NodeOptions::use_intra_process_comms(true)` 开启；发布必须 `std::unique_ptr`（独占）或 `std::shared_ptr`（共享）语义，裸 `publish(msg)` 不享受零拷贝；发布与订阅节点必须加入**同一个执行器**；缓冲策略 `intra_process_buffer_type` 可选 KeepLast/KeepAll（配合 QoS depth）。课程「同进程 talker/listener 延迟对比」即此意。

**要点 3：执行器差异与优化**。单线程执行器最简单但回调互相阻塞；多线程执行器并行处理回调时注意线程安全；静态单线程执行器（StaticSingleThreadedExecutor）减少调度开销，适合嵌入式。优化方向：合并节点进容器、减少 QoS 深度、避免不必要拷贝。

**要点 4：Python 实现**。rclpy 通过 `NodeOptions`/上下文同样可开启进程内通信，但零拷贝收益不如 C++ 显著（Python 有对象开销）；课程以框架搭建 + 实现 + 小结收尾，强调原理一致、性能不同。

**要点 5：话题统计（Topic Statistics）**。为订阅开启统计后，中间件按周期把该话题的年龄、频率、抖动、样本数等指标发布到 `/statistics`（`statistics_msgs/MetricsMessage`），用于观测链路质量而不侵入业务代码。

**要点 6：话题内容过滤（Content Filtering）**。订阅端配置 SQL-92 WHERE 风格过滤表达式（如 `temperature > %0`），不满足条件的消息在中间件层即被丢弃，回调与带宽都不再为垃圾数据买单——ARM 板上订阅高频率传感器话题时尤其有用。

**要点 7：QoS 与话题管理配合**。统计话题用可靠（RELIABLE）+ 适度深度保证指标不丢；传感器数据用 `SensorDataQoS`（Best Effort）降低开销；内容过滤减少回调次数后，可把 QoS 深度调小以省内存。参数事件、统计话题都应纳入统一的 QoS 与命名规范管理。

**要点 8：参数事件**。每个节点的参数增、删、改都会向全局话题 `/parameter_events` 发布 `rcl_interfaces/ParameterEvent`。两种用法：直接订阅该话题做全局审计；或用 `rclcpp::AsyncParametersClient::on_parameter_event()` 监听指定节点（如在线调参整定 PID）。C++ 实现分「基本流程」与「监听其他节点参数」两步，Python 实现分「添加监听」与「事件处理」两步。

### 21.2.3 第3课 组件开发与启动与插件系统开发

**核心概念**：组件（Component）是「可被容器动态加载的节点」，插件（pluginlib）是「可被运行时替换的算法单元」。二者共同支撑了 nav2 等框架的架构：节点合并进进程降延迟，算法按配置替换保扩展。

**要点 1：组件使用基本流程与 `ros2 component` 指令**。先有组件化节点类 → 编译为共享库并注册 → 用 `ros2 component list / types / standalone / load / unload` 管理容器中的组件；`load` 可在运行时把组件装入已运行的容器，`standalone` 以独立进程方式运行同一组件。

**要点 2：talker/listener 组件实现**。节点类构造函数只接收 `const rclcpp::NodeOptions &` 并透传给 `Node` 基类；源文件末尾 `RCLCPP_COMPONENTS_REGISTER_NODE` 完成注册；CMake 用 `rclcpp_components_register_nodes()` 声明插件名，`package.xml` 声明 `rclcpp_components` 依赖。listener 组件同理，收发话题对接。

**要点 3：容器与 launch 启动**。`component_container`（单线程）/ `component_container_mt`（多线程）是容器可执行文件；launch 文件用 `ComposableNodeContainer` + `ComposableNode` 描述装配，`extra_arguments` 可为每个组件开启进程内通信——这正是「组件化 + 零拷贝」组合的入口。

**要点 4：pluginlib 插件开发五步**。① 创建功能包（声明 `pluginlib` 依赖）；② 插件基类（纯虚接口 + 虚析构函数）；③ 插件类（继承基类 + `PLUGINLIB_EXPORT_CLASS` 导出宏）；④ 插件描述 XML（`<class type=... base_class_type=...>`）并导出到 `package.xml` 的 `<export><your_plugin_tag plugin="${prefix}/xxx.xml"/>`；⑤ 加载端用 `pluginlib::ClassLoader<Base>` 按名字创建实例：

```xml
<!-- pluginlib_demo/plugins.xml：插件描述文件 -->
<library path="planner_plugins">
  <class name="planner_plugins/StraightPlanner" type="planner_plugins::StraightPlanner"
         base_class_type="planner_base::PlannerBase">
    <description>直线规划插件</description>
  </class>
</library>
```

**要点 5：插件的价值与演示**。课程用「创建新插件 → 灵活配置插件」两步演示扩展性——新增一种规划/滤波算法只需新增一个插件类与一行 XML，主程序与加载代码零改动；通过参数（YAML）即可在 StraightPlanner 与新插件间切换，这正是 nav2 中 `plugin: "nav2_navfn_planner/NavfnPlanner"` 一类配置的工作原理。

## 21.3 重点与难点

1. **生命周期回调的状态边界**：`on_activate/on_deactivate` 里只启停「工作」，资源的创建/释放放在 `on_configure/on_cleanup`；否则 cleanup 后再 configure 会因资源已释放而崩溃。
2. **零拷贝的成立条件**：同进程 + 双方都开启 `use_intra_process_comms` + 发布端 `std::unique_ptr` + 同一执行器，四者缺一收益归零；跨进程时仍走序列化，属于正常现象。
3. **内容过滤的表达式语义**：只支持 SQL-92 WHERE 的子集，字段名必须与消息字段一致、占位符 `%0` 从 0 开始编号，且需要 RMW（如 Fast DDS / Connext）支持，不支持时会退化为不过滤。
4. **组件与插件不要混淆**：组件封装的是「节点」（进程内加载、管理话题与参数），插件封装的是「算法单元」（被节点或框架加载、只暴露接口）；一个组件容器可以承载多个组件，一个节点内部可以加载多个插件。
5. **ARM 板上的部署取舍**：编译限流防 OOM、桌面调通再上板、用统计与参数事件做线上观测；Debug 符号留给 PC，板上用 Release。

### 21.4.2 生命周期节点（要点代码）

```cpp
class MyNode: public rclcpp_lifecycle::LifecycleNode{
public:
    MyNode():rclcpp_lifecycle::LifecycleNode("my_lifecycle_node_cpp"){}
    CallbackReturn on_configure(const rclcpp_lifecycle::State &){
        RCLCPP_INFO(this->get_logger(),"节点配置......");
        return CallbackReturn::SUCCESS;
    }
    CallbackReturn on_activate(const rclcpp_lifecycle::State &){
        RCLCPP_INFO(this->get_logger(),"节点激活------------");
        return CallbackReturn::SUCCESS;
    }
    // on_deactivate / on_cleanup / on_shutdown 同理
};
```

资源管理约定：`on_configure` 只创建发布者/打开设备，`on_activate` 创建定时器并 `LifecycleNode::on_activate(s)` 激活生命周期发布者，`on_deactivate` 只 `timer_.reset()` 停工作，`on_cleanup`/`on_shutdown` 才释放全部资源（参考 `lifecycle_demo/src/sensor_lifecycle_node.cpp` 模式）。Python 版对应 `LifecycleNode`，命令完全相同：

```bash
ros2 run lifecycle_demo sensor_lifecycle
ros2 lifecycle set /sensor_lifecycle configure   # Unconfigured -> Inactive
ros2 lifecycle set /sensor_lifecycle activate    # Inactive -> Active，开始发布
ros2 lifecycle get /sensor_lifecycle             # 查看当前状态
```

### 21.4.3 进程内通信

关键点是通过 `NodeOptions` 为两个节点开启进程内通信，并放入**同一个执行器**：

```cpp
// 4-1.节点设置：开启进程内通信；
rclcpp::NodeOptions options;
options.use_intra_process_comms(true);
// 4-2.单线程执行器 + 两个节点；
rclcpp::executors::SingleThreadedExecutor executor;
executor.add_node(std::make_shared<MinimalPublisher>(options));
executor.add_node(std::make_shared<MinimalSubscriber>(options));
executor.spin();
```

> 兼容提示：老式写法 `rclcpp::SubscriptionOptions.use_intra_process_comm = IntraProcessSetting::Enable` 在 Jazzy 下会导致
> 订阅注册异常（节点不上线、回调不触发）；请使用 **`NodeOptions::use_intra_process_comms(true)`**（官方示例写法）。

发布侧配套：`auto msg = std::make_unique<std_msgs::msg::String>(); ... pub->publish(std::move(msg));`——所有权移交即零拷贝。

### 21.4.5 参数事件

```cpp
// param_demo/src/param_event_watcher.cpp（核心）
// ① 直接订阅全局 /parameter_events：审计所有节点的参数增删改
auto sub = node->create_subscription<rcl_interfaces::msg::ParameterEvent>(
  "/parameter_events", 100, [](rcl_interfaces::msg::ParameterEvent::ConstSharedPtr ev) {
    for (const auto & p : ev->changed_parameters)
      RCLCPP_INFO(rclcpp::get_logger("audit"), "%s: %s changed",
                  ev->node.c_str(), p.name.c_str()); });

// ② 只监听指定节点（如驱动节点）：调参整定常用
auto client = std::make_shared<rclcpp::AsyncParametersClient>(node, "/driver_node");
auto handle = client->on_parameter_event(
  [](const rcl_interfaces::msg::ParameterEvent & ev) {
    for (const auto & p : ev->new_parameters)
      RCLCPP_WARN(rclcpp::get_logger("tuner"), "driver 新参数 %s", p.name.c_str()); });
```

本节点自身的参数修改事件用 `add_on_set_parameters_callback` 监听（`demo_param_events(_py)` 两版实现一致）。

### 21.4.6 组件与插件

```cmake
# composition_demo/CMakeLists.txt 关键行
add_library(talker_component SHARED src/talker_component.cpp)
ament_target_dependencies(talker_component rclcpp rclcpp_component std_msgs)
rclcpp_components_register_nodes(talker_component "TalkerComponent")
```

节点类构造函数只接收 `const rclcpp::NodeOptions &`，源文件末尾 `rclcpp_components::RegisterNodeMacro` 注册为组件。插件三件套：基类包 `plugin_base`（纯虚接口 + 导出头文件）；插件包 `plugin_impl`（`PLUGINLIB_EXPORT_CLASS(polygon_plugins::Triangle, polygon_base::RegularPolygon)` + `pluginlib_export_plugin_description_file(plugin_base plugin_impl.xml)`）；加载方 `plugin_loader`：

```cpp
pluginlib::ClassLoader<polygon_base::RegularPolygon> loader("plugin_base","polygon_base::RegularPolygon");
auto triangle = loader.createSharedInstance("polygon_plugins::Triangle");
auto square   = loader.createSharedInstance("polygon_plugins::Square");
```

> 注意：ClassLoader 第一个参数是**基类所在包名**（插件通过 ament 索引注册到该包名下），写成插件包名会报 "Declared types are (empty)"。

## 21.6 与 ROS2 / 机器人开发的关联

1. **ARM 边缘设备上的资源受限部署**：colcon 的增量构建、编译限流与 `ros-base` 装配思路，直接决定树莓派上的部署成功率；话题统计与 `/parameter_events` 是边缘端不加日志刷屏也能观测系统的手段。
2. **组件化零拷贝降低延迟**：把感知→规划链路装进 `component_container_mt` 并开启 `use_intra_process_comms`，图像、点云等大消息延迟与 CPU 占用显著下降，是 CPU 弱平台上实时性的关键。
3. **生命周期节点管理硬件驱动的启动/关闭**：雷达、IMU、电机驱动做成生命周期节点后，可由 launch 或上位机统一 `configure/activate`，故障时 `deactivate/cleanup` 安全断电，符合机器人功能安全的启停规范。
4. **插件化算法（如 nav2 插件）**：nav2 的规划器、控制器、代价地图层全部以 pluginlib 插件交付；本章的插件骨架就是阶段 8 中替换 `NavfnPlanner`、`DWBController` 或自研算法的前置技能。

1. 生命周期节点从 Inactive 状态再次开始发布数据，需要触发哪两个迁移？`on_cleanup` 与 `on_deactivate` 的职责区别是什么？

> 参考答案要点：1）先 `activate`（Inactive→Active）即可继续发布，无需重新 configure；`on_deactivate` 停止工作但保留资源，`on_cleanup` 释放资源回到 Unconfigured。2）同容器零拷贝下延迟与 CPU 明显更低，因为省去序列化与两次缓冲拷贝。3）插件描述 XML + `PLUGINLIB_EXPORT_CLASS` + `ClassLoader::createSharedInstance` 三件套齐全，YAML 中插件名与 XML 中 `<class name>` 一致。

## 21.8 常见问题（FAQ）

- **Q：`colcon build` 时树莓派卡死或被 OOM 杀掉怎么办？** A：用 `--parallel-workers 1` 或 `-j1` 限制并行编译，关闭桌面环境释放内存，必要时添加 2GB 以上 swap，并优先 `--packages-select` 只编译改动的包。
- **Q：为什么零拷贝没有生效？** A：逐条检查四个条件——两节点在同一进程、双方 `use_intra_process_comms(true)`、发布端用 `std::unique_ptr` 发布、两节点加入同一执行器；任一不满足都会回退到普通拷贝路径。
- **Q：`ros2 lifecycle set` 报 transition 无效？** A：状态机只接受当前状态允许的迁移，先 `ros2 lifecycle get` 查状态；例如 Active 状态要先 `deactivate` 再 `cleanup`，不能直接 configure。
- **Q：`ros2 node list` / `ros2 lifecycle get` 长时间返回空或 "Node not found"？** A：ros2 守护进程缓存陈旧（端到端核对中的真实环境坑）。`ros2 daemon stop` 后重试——daemon 停止时 CLI 直接发现节点，服务实际已上图，并非代码问题。
- **Q：内容过滤表达式写了却不生效？** A：确认 RMW 支持内容过滤（Fast DDS/Connext 一般支持，CycloneDDS 可能不支持），表达式字段名要与消息定义字段一致，参数占位符从 `%0` 编号；不支持时订阅会退化为接收全部消息。
- **Q：组件（Component）和插件（pluginlib）到底怎么选？** A：要合并进程、统一生命周期与参数管理，用组件；要在算法层面热插拔、按配置替换（nav2 风格），用插件。两者可叠加：组件节点内部加载算法插件。

## 21.9 本章小结

| 特性 | 一句话价值 |
| --- | --- |
| 生命周期 | 系统化管控节点「配置→激活→关闭」，故障可恢复 |
| 进程内通信 | 同进程零拷贝，延迟/负载显著下降 |
| 组件 | 运行时动态装载节点，共享进程与执行器 |
| pluginlib | 运行时扩展算法实现，主程序零改动 |
