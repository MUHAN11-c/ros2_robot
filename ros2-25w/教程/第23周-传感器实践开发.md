## 23.2 知识点梳理

### 23.2.1 第1课 传感器之相机和IMU详解与仿真案例（3h15m · 26 节）

- **核心概念**：相机（Camera）把三维世界投影为二维图像，提供颜色/纹理/语义信息；IMU（Inertial Measurement Unit，惯性测量单元）测量自身角速度与线加速度，提供高频的姿态与运动信息。二者常与雷达/里程计互补使用。

#### 相机概念、作用与特点（视频 1-1）

作用：目标识别与跟踪、视觉 SLAM、远程监控图传。特点：信息量最大（颜色+纹理+语义）；数据率高、计算开销大；受光照/遮挡影响；单目无直接深度信息。

#### 相机分类（视频 1-2）

| 类型 | 代表 | 输出 | 典型用途 |
|---|---|---|---|
| 单目（Monocular） | USB 摄像头 | `Image` | 视觉识别、监控 |
| 双目（Stereo） | ZED、小觅 | 左右 `Image` + 视差/深度 | 稠密深度估计 |
| 深度（Depth / RGB-D） | RealSense、Kinect、奥比中光 | `Image` + `PointCloud2` + `CameraInfo` | 避障、三维重建 |
| 其他 | 鱼眼、全景、红外 | `Image` | 特殊场景 |

#### 单目相机使用（视频 1-3 ~ 1-7）

- **硬件准备与软件安装**：USB 相机插入后先确认识别与权限：

```bash
ls /dev/video*                      # 一颗摄像头常占用 video0/video1 两个节点
groups | grep video                 # 无输出则 sudo usermod -aG video $USER 后重新登录
sudo apt install ros-humble-usb-cam # 课程写法；Jazzy 换 ros-jazzy-usb-cam 或源码编译
```

- **usb_cam 功能包**（1-4）：发布 `/image_raw`（`sensor_msgs/Image`）与 `/camera_info`（`sensor_msgs/CameraInfo`）。关键参数：`video_device`、`pixel_format`（YUYV/MJPEG）、`image_width`/`image_height`、`framerate`、`frame_id`。
- **自定义功能包封装**（1-5 ~ 1-7，框架搭建/代码结构/代码修正三讲）：订阅原始图像 → 处理 → 统一话题名转发；要点是用 `image_transport` 而非裸 `Publisher<Image>`，才能免费获得 `compressed` 等传输插件；修正点集中在 encoding 声明与时间戳（用消息自带 `header.stamp` 而非 `now()`）。

#### 深度相机使用（视频 1-8）

除 RGB 图外输出对齐深度图与 `PointCloud2`；使用要点：depth 与 color 的配准（对齐模式）、深度有效范围（典型 0.3–5 m，过近/过远为无效值）、`CameraInfo` 内参一致性。

#### Image 消息逐字段（视频 1-9）

`sensor_msgs/Image` 字段表：

| 字段 | 类型 | 含义 | 本案例取值 |
|---|---|---|---|
| `header` | std_msgs/Header | `stamp`（采集时刻）+ `frame_id`（相机坐标系名，供 tf2/rviz2 关联） | frame_id = camera |
| `height` | uint32 | 图像高（像素行数） | 240 |
| `width` | uint32 | 图像宽（像素列数） | 320 |
| `encoding` | string | 像素编码，决定 `data` 的字节解释：`mono8`/`rgb8`/`bgr8`/`rgba8`/`16UC1`（深度毫米）/`32FC1`（深度米）等 | mono8（每像素 1 字节灰度） |
| `is_bigendian` | uint8 | 字节序标志；x86/ARM 小端机为 0 | 0 |
| `step` | uint32 | 每行字节数 = width × 每像素字节数（个别驱动含行对齐 padding） | 320（= 320×1） |
| `data[]` | uint8[] | 行优先（row-major）裸字节，长度 = step × height | 76800（= 320×240） |

> **注意：** `encoding` 决定 `data` 的解析方式，`bgr8` 与 `rgb8` 通道顺序相反；OpenCV 的 `cv::Mat` 默认 BGR，与 `rgb8` 话题混用会出现「蓝蓝的图像」。深度图按 float/uint16 解析前务必核对 encoding。

配套 `sensor_msgs/CameraInfo`（usb_cam 与标定都会发布）：`distortion_model`（`plumb_bob` 等）、内参 `k`（3×3：fx/0/cx，0/fy/cy，0/0/1）、矫正矩阵 `r`、投影矩阵 `p`、`roi` 与 `binning_x/y`。

#### 单目相机仿真案例（视频 1-10 ~ 1-17）

需求：不接真实相机，周期性组织并发布一幅自造黑白条纹 `Image` 验证图像链路。流程（与雷达/点云仿真同构）：案例分析（定话题/消息/频率）→ 框架搭建（发布者+定时器）→ 组织图片基本参数（height/width/encoding/is_bigendian/step）→ 图片数据组织（`data.resize(height*width)`，每 20 列交替黑白，逐帧整体翻转形成闪烁条纹）→ 打时间戳发布 → 测试与小结。C++/Python 各三讲按此拆分，真实代码分步讲解见 23.4.1/23.4.2。

#### IMU 概念与作用、优缺点（视频 2-1 ~ 2-2）

IMU = 陀螺仪（角速度）+ 加速度计（线加速度），高档型号集成磁力计可输出绝对航向。作用：为姿态估计与融合定位提供高频运动观测，是 EKF/互补滤波的核心输入。

| 优点 | 缺点 |
|---|---|
| 采样率高（100–1000 Hz） | 加速度二次积分误差随时间平方增长（漂移） |
| 不依赖外部环境（无遮挡问题） | 陀螺零偏与温漂需标定补偿 |
| 短期精度高、延迟低 | 磁力计受磁场干扰；廉价 MEMS 噪声大 |

结论：IMU 短期准、长期漂，必须与里程计/GNSS 等绝对源融合使用。

#### IMU 基本使用与消息接口逐字段（视频 2-3 ~ 2-4）

基本使用：`ros2 topic hz /imu` 确认采样率、`ros2 run tf2_ros tf2_echo base_link imu_link` 确认安装外参；rviz2 中可加 Imu 显示件或用 TF 观察姿态变化。

`sensor_msgs/Imu` 字段表：

| 字段 | 类型 | 单位/含义 |
|---|---|---|
| `header` | std_msgs/Header | frame_id 一般为 imu_link |
| `orientation` | geometry_msgs/Quaternion（x, y, z, w） | 姿态四元数（姿态解算/磁力计融合结果） |
| `orientation_covariance` | float64[9] | 3×3 姿态协方差；首元素 [0] = -1 表示该传感器无姿态输出 |
| `angular_velocity` | geometry_msgs/Vector3（x, y, z） | 角速度，单位 rad/s |
| `angular_velocity_covariance` | float64[9] | 角速度协方差；无输出轴 [0] = -1 |
| `linear_acceleration` | geometry_msgs/Vector3（x, y, z） | 线加速度，单位 m/s²；静止水平放置时 z 轴约 +9.81（含重力） |
| `linear_acceleration_covariance` | float64[9] | 线加速度协方差；无输出轴 [0] = -1 |

四元数与欧拉角互换：Python 用 `tf_transformations`，C++ 用 `tf2/utils.h` 的 `getYaw`，避免手写公式出错。

#### IMU 案例（视频 2-5 ~ 2-9）

需求：订阅 `/imu`，回调中解析并打印姿态四元数、角速度、线加速度三组数据。C++ 两讲 = 框架搭建 + 核心实现（课程此讲使用真实 Mycar 板载 IMU 实拍，并在 rviz2 中以 TF 显示 world→mycar 随姿态变化）；Python 一讲完整实现。代码见 23.4.3/23.4.4。

### 23.2.2 第2课 GNSS详解与轮式里程计标定与融合（3h57m · 33 节）

- **核心概念**：GNSS（Global Navigation Satellite System，全球导航卫星系统，含 GPS/北斗/GLONASS/Galileo）提供绝对经纬度与海拔；轮式里程计标定（Odometry Calibration）是用实测修正轮径/轮距参数，让里程计推算逼近真实运动。

#### GNSS 概念、特点与分类（视频 1-1 ~ 1-2）

作用：全局绝对定位，无累积漂移，与里程计/IMU 互补。特点：更新率低（1–10 Hz）；精度受环境影响（城市峡谷、树荫遮挡、多径）；输出是球面坐标，必须投影到平面才能与局部建图/导航融合。分类（按精度与改正方式）：单点定位（米级）、差分 DGNSS（亚米级）、RTK 载波相位差分（厘米级，需基站/网络服务）。

#### GNSS 基本使用与消息接口逐字段（视频 1-3 ~ 1-4）

驱动节点发布 `/fix`；调试：`ros2 topic echo /fix --once`、`ros2 topic hz /fix`。`sensor_msgs/NavSatFix` 字段表：

| 字段 | 类型 | 含义 |
|---|---|---|
| `header` | std_msgs/Header | frame_id 常用 gps 或 map |
| `status` | sensor_msgs/NavSatStatus | 定位状态与所用卫星系统（见下） |
| `latitude` | float64 | 纬度，单位度，北正南负 |
| `longitude` | float64 | 经度，单位度，东正西负 |
| `altitude` | float64 | 海拔，单位米（相对椭球面，与海拔高有差异） |
| `position_covariance` | float64[9] | 3×3 位置协方差，单位 m²，ENU（东北天）顺序 |
| `position_covariance_type` | uint8 | 0=未知 / 1=近似 / 2=对角已知 / 3=已知 |

`sensor_msgs/NavSatStatus`：`status` 枚举 `-1 STATUS_NO_FIX`（未定位）、`0 STATUS_FIX`（常规定位）、`1 STATUS_SBAS_FIX`、`2 STATUS_GBAS_FIX`；`service` 位标志 `SERVICE_GPS/GLONASS/GALILEO/BEIDOU/…` 指示参与解算的星座。**消费逻辑必须先判 status 再用坐标**——未定位时 lat/lon 可能为 0 或 NaN。

#### GNSS 案例（视频 1-5 ~ 1-17）

需求（案例分析 01/02）：把 GNSS 历史定位点组织成 rviz2 可视化轨迹（`nav_msgs/Path`）；难点全在坐标系与投影——经纬度是角度量，直接当米用毫无意义。C++ 六讲对应实现步骤（与 23.4.5 代码注释一一对应）：

1. 框架搭建：订阅 `/fix` + 发布 `/gnss_path`；
2. Path 数据组织之标头：构造函数中 `path_.header.frame_id = "map"`（rviz2 固定坐标系）；
3. 坐标系确定：以原点为中心的平面直角坐标（ENU 思想：x 向东、y 向北）；
4. 原点确定：以**首个有效定位**为原点（`status >= 0` 且纬度非零才采纳），打印原点经纬度；
5. 经纬度换算：等距圆柱近似——`x = (lon-lon0)·111319.49079327358·cos(lat0·π/180)`，`y = (lat-lat0)·111319.49079327358`（111319.49 m 为赤道 1° 弧长；工程上更推荐 `robot_localization/navsat_transform_node` 或 `GeographicLib` 的 UTM 投影）；
6. 数据组织完成：每个有效 `/fix` 转成 `PoseStamped` 追加进 `path_.poses`，刷新 Path 标头后整体重发。

Python 三讲（框架搭建 / 部分字段设置 / 数据组织）覆盖同样步骤，见 23.4.6。`nav_msgs/Path` = `header` + `poses[]`（每项 `geometry_msgs/PoseStamped` = `header + pose`，本案例只填 position.x/y）。

#### 轮式里程计标定（小节 2，视频 1-6）

场景：里程计由轮速积分推算位姿，轮径磨损、轮距装配误差造成系统性偏差（走 10 m 报 9.3 m、转 360° 报 350°）。标定两步：

| 步骤 | 标定流程 | 实现 |
|---|---|---|
| 线性位移标定 | 直行标称距离（5–10 m），对比 `/odom` 累计位移与实测值 | 脚本发布 `/cmd_vel` 线速度、积分 `/odom`；修正系数 = 目标距离 / 实测距离，乘到轮径参数 |
| 角速度标定 | 原地旋转标称角度（≥2 圈），对比 `/odom` 累计 yaw | 发布角速度、四元数换算累计 yaw；轮距新值 = 轮距旧值 ×（实测转角 / 指令转角） |

实验设计要点：直线够长、圈数够多、地面摩擦一致、多次实验取平均（3–5 次）。

#### 轮式里程计与 IMU 融合 · robot_localization（小节 3，视频 0-9 讲）

| 步骤 | 内容 |
|---|---|
| 1 简介安装 | `sudo apt install ros-humble-robot-localization`（Jazzy 换前缀） |
| 2 包简介 | 提供 `ekf_node`（扩展卡尔曼滤波）与 `ukf_node`（无迹卡尔曼），支持 odom/imu/twist/gps 多源输入 |
| 3 融合准备 | 明确各传感器坐标系、话题、QoS；准备 EKF 参数 yaml |
| 4 launch 框架 | 一个 launch 集成底盘驱动、IMU 静态变换、EKF 节点 |
| 5 底盘实现 | 底盘节点发布 `/odom`（轮速积分）与 `odom → base_link` tf |
| 6 IMU 坐标变换 | `static_transform_publisher` 或 URDF 定义 `base_link → imu_link` |
| 7 EKF 融合 | `ekf_node` 订阅 `/odom` + `/imu`，发布 `/odometry/filtered` 与 `odom → base_link`（EKF 版） |
| 8 执行验证 | rviz2 对比 `/odom` 与 `/odometry/filtered` 轨迹，融合后应更平滑、漂移更小 |

EKF 关键配置思想：每个输入源用 `odom0`/`imu0` 系列参数声明话题，布尔矩阵 `odom0_config` 指定融合哪些状态量（如 IMU 只融合 yaw 角速度与加速度、不融合其绝对姿态）；处理好「谁发布 `odom → base_link`」的唯一性——开启 EKF 的 `publish_tf` 后，底盘端要关掉自己的 tf 发布。

### 23.2.3 第3课 激光雷达工具和相机使用进阶（4h01m · 31 节）

- **核心概念**：原始传感器数据要经过「过滤 → 融合 → 格式转换」的加工流水线才能喂给 SLAM/导航；相机进阶则解决远程传输、标定精度与多相机扩展。

#### 雷达过滤器 laser_filters（视频 1-1 ~ 1-6）

功能包提供 `scan_to_scan_filter_chain` 节点，以插件链加工 `/scan`：

| 插件 | 作用 |
|---|---|
| `LaserScanRangeFilter` | 裁剪量程外/无效测距（inf/nan 置为替换值） |
| `LaserScanAngularBoundsFilter` | 裁剪角度扇区（屏蔽机器人自身结构遮挡） |
| `LaserScanSpeckleFilter` | 滤孤立噪点/飞点 |
| `LaserScanShadowsFilter` | 滤阴影/多次反射伪影 |

应用案例：① 过滤无效数据（把 inf/nan 替换为 `.nan` 统一标记后由下游剔除）；② 设置有效范围（仅保留 0.15–8 m，避免近处自遮挡回波与远端噪声）。

#### 雷达融合 ira_laser_tools（视频 1-7 ~ 1-16）

场景：单雷达视野受限（如 240°），需前后双雷达拼接 360°。`laserscan_multi_merger` 节点按各雷达 tf 把多路 `/scan` 融合为一路。案例五步：需求分析 → **雷达端口重映射**（USB 端口号会漂移，用 udev 规则按序列号固定符号链接）→ 启动两个雷达（各自命名空间 `/scan_front`、`/scan_rear`）→ **坐标系集成**（分别建 `laser_front_link`/`laser_rear_link` 静态 tf 并统一到 `base_link`）→ 融合实现（配置 `destination_frame`、`cloud_destination_topic`/`scan_destination_topic`、`scan_source_topics`）。扩展案例：融合后再过滤（merger 输出接 `scan_to_scan_filter_chain`）。

#### 点云与激光扫描互转（视频 1-17 ~ 1-21）

| 方向 | 工具 | 典型用途 |
|---|---|---|
| LaserScan → PointCloud2 | `laser_geometry::LaserProjection`（C++ API） | 2D 雷达数据并入三维处理管线、多传感器同视图显示 |
| PointCloud2 → LaserScan | `pointcloud_to_laserscan` 节点 | 3D 雷达/深度相机「压扁」成 2D 扫描，喂给 2D SLAM 与导航 |

转换时要指定 `target_frame`、高度裁剪区间（`min_height`/`max_height`，只取地面以上 0.1–1.0 m 的点做避障）与角度/量程范围。

#### 相机进阶 · 远程图传（视频 2-1 ~ 2-3）

机器人端跑相机节点、PC 端看图，原始图带宽大（640×480×3×30 ≈ 27 MB/s），需压缩：用 `image_transport` 的 `compressed` 传输插件发布 `/image_raw/compressed`（`sensor_msgs/CompressedImage`，JPEG/PNG 载荷），PC 端解压显示（`image_transport` 订阅方自动回退压缩话题，或 `rqt_image_view` 直接选压缩话题）；本地解压缩一讲讲解 `CompressedImage.format` 与 `cv_bridge` 解码为 `cv::Mat`。

#### 相机进阶 · 标定与多相机（视频 2-4 ~ 2-10）

标定求解内参（焦距 fx/fy、主点 cx/cy、畸变系数）与外参。流程：打印棋盘格标定板 → `ros2 run camera_calibration cameracalibrator --size 8x6 --square 0.024 image:=/image_raw camera:=/camera` → 移动标定板采集多角度样本（X/Y/Size/Skew 进度条收敛）→ 保存得到 `camera_info` YAML → 使用标定参数（发布 `/camera_info`、`image_proc` 去畸变）。多相机：设备号 `/dev/video*` 开机后随机漂移，**端口绑定**用 udev 规则（按 USB 序列号固定别名如 `/dev/camera_front`）；再添加前/后相机（各自命名空间 `/front_camera`、`/rear_camera`，独立 `CameraInfo` 与 tf 链杆）。

## 23.3 重点与难点

1. **Image 的 encoding 与内存布局**：`step = width × 每像素字节数`（可能含行对齐 padding），`data.size() = step × height`。用 `cv_bridge` 转 `cv::Mat` 时选错编码会得到色彩错乱或直接异常。
2. **GNSS 的坐标投影**：经纬度不能直接当平面坐标用。统一做法：以首帧为原点做 ENU 投影（或交给 `navsat_transform_node`），并声明 `frame_id`；忘了投影，轨迹在 rviz2 中只是一个「远处的小点」。
3. **IMU 漂移与协方差**：IMU 短期准、长期漂。EKF 融合时必须为各传感器配置合理的协方差（不确定度），否则「谁嗓门大听谁的」，融合结果反而更差。
4. **多雷达融合的坐标系前提**：merger 依赖 tf 把各路扫描变换到 `destination_frame`；tf 缺失或时间戳不同步时，融合结果是「错位的拼图」。先 `tf2_echo` 验证每路雷达的静态变换再启动融合。
5. **里程计标定的实验设计**：直行距离要长（≥5 m）、旋转圈数要多（≥2 圈）、地面摩擦一致、电池电压稳定；单次实验误差大，取 3–5 次平均。
6. **仿真 → 实机迁移要点**：仿真中传感器无噪声、时间戳完美；实机上要考虑驱动延迟、时钟同步（`use_sim_time` 切换）、丢帧与抖动，代码里时间相关逻辑一律用消息自带的 `header.stamp` 而不是 `now()`。
7. **传感器消息的「有效性判别」**：NavSatFix 先看 `status`，Imu 无输出轴协方差首元素为 -1，LaserScan 无效点为 inf/nan——不判别就会把垃圾数据当真值积分。

### 23.4.1 单目相机仿真 · C++（cpp03_camera_sim）

完整源码 `src/camera_sim.cpp`：

```cpp
/*
    需求：单目相机仿真 —— 周期性组织并发布 Image 消息(模拟黑白条纹图)。
*/
// 1.包含头文件；
#include "rclcpp/rclcpp.hpp"
#include "sensor_msgs/msg/image.hpp"

using namespace std::chrono_literals;

// 3.自定义节点类；
class CameraSim: public rclcpp::Node{
public:
    CameraSim():Node("camera_sim_node_cpp"){
        RCLCPP_INFO(this->get_logger(),"单目相机仿真节点创建!");
        pub_ = this->create_publisher<sensor_msgs::msg::Image>("image_raw",10);
        timer_ = this->create_wall_timer(100ms,std::bind(&CameraSim::on_timer,this));
    }
private:
    void on_timer(){
        // 1.组织图片基本参数；
        sensor_msgs::msg::Image image;
        image.header.frame_id = "camera";
        image.height = 240;
        image.width = 320;
        image.encoding = "mono8";
        image.is_bigendian = 0;
        image.step = image.width;
        // 2.组织图片数据：黑白条纹；
        image.data.resize(image.height * image.width);
        static bool flip = false;
        for (uint32_t r = 0; r < image.height; ++r) {
            for (uint32_t c = 0; c < image.width; ++c) {
                bool band = ((c / 20) % 2 == 0) ^ flip;
                image.data[r * image.width + c] = band ? 255 : 0;
            }
        }
        flip = !flip;
        image.header.stamp = this->now();
        pub_->publish(image);
    }
    rclcpp::Publisher<sensor_msgs::msg::Image>::SharedPtr pub_;
    rclcpp::TimerBase::SharedPtr timer_;
};

int main(int argc, char ** argv)
{
    rclcpp::init(argc,argv);
    rclcpp::spin(std::make_shared<CameraSim>());
    rclcpp::shutdown();
    return 0;
}
```

分步讲解（对照视频三讲）：

- **01 框架搭建**：构造函数创建 `image_raw` 发布者（队列 10）与 100ms 周期定时器（10 Hz，接近真实 USB 相机帧率）；`main` 三段式 init/spin/shutdown。
- **02 组织图片基本参数**：回调内先填五个「元数据」字段——`frame_id = "camera"`（rviz2 中 Fixed Frame 需能解析该坐标系）、`height/width = 240/320`（QVGA）、`encoding = "mono8"`（每像素 1 字节灰度，数据量最小、链路验证最稳）、`is_bigendian = 0`（小端机）、`step = width`（mono8 每行字节数恰为宽度）。若改 rgb8，则 `step = width * 3`、`data` 长度变为 3 倍。
- **03 图片数据组织以及小结**：`data.resize(height*width)`（= 76800 字节）先分配再写入；双层循环按行优先寻址 `data[r*width + c]`，`(c/20)%2` 让每 20 列组成一条竖向色带，`^ flip` 让黑白逐帧整体翻转（10 Hz 闪烁便于肉眼确认「图在动」）；`static bool flip` 跨回调保留状态；数据就绪后补 `header.stamp` 再发布。

`CMakeLists.txt` 关键行（包内实际内容）：`find_package(rclcpp/sensor_msgs REQUIRED)` → `add_executable(camera_sim src/camera_sim.cpp)` → `ament_target_dependencies(camera_sim rclcpp sensor_msgs)` → `install(TARGETS camera_sim DESTINATION lib/${PROJECT_NAME})`；`package.xml` 依赖 `rclcpp + sensor_msgs`（ament_cmake）。

### 23.4.2 单目相机仿真 · Python（py03_camera_sim）

完整源码 `py03_camera_sim/camera_sim_py.py`：

```python
# -*- coding: utf-8 -*-
"""
    需求：单目相机仿真（Python实现）—— 周期性组织并发布 Image 消息(黑白条纹)。
"""
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import Image


class CameraSimPy(Node):

    def __init__(self):
        super().__init__("camera_sim_node_py")
        self.get_logger().info("单目相机仿真节点创建!(python)")
        self.pub = self.create_publisher(Image, "image_raw", 10)
        self.timer = self.create_timer(0.1, self.on_timer)
        self.flip = False

    def on_timer(self):
        # 组织图片基本参数；
        image = Image()
        image.header.frame_id = "camera"
        image.header.stamp = self.get_clock().now().to_msg()
        image.height = 240
        image.width = 320
        image.encoding = "mono8"
        image.is_bigendian = 0
        image.step = image.width
        # 组织图片数据：黑白条纹；
        data = bytearray(image.height * image.width)
        for r in range(image.height):
            for c in range(image.width):
                band = ((c // 20) % 2 == 0) ^ self.flip
                data[r * image.width + c] = 255 if band else 0
        image.data = bytes(data)
        self.flip = not self.flip
        self.pub.publish(image)


def main():
    rclpy.init()
    rclpy.spin(CameraSimPy())
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

与 C++ 的三处差异（视频 Python 三讲强调点）：

1. `flip` 是实例属性 `self.flip`（Python 无 static 局部变量）；`create_timer(0.1, …)` 以秒为单位，C++ 用 `100ms` 字面量。
2. `data` 用 `bytearray` 可变缓冲逐字节填充，最后 `bytes(data)` 一次性赋给 `image.data`。
3. 时间戳用 `self.get_clock().now().to_msg()`，在组织数据**前**打好——顺序与 C++ 相反但同样有效，工程上建议统一「填完数据再打戳」。

入口注册（`setup.py` 实际内容节选）：`'camera_sim_py = py03_camera_sim.camera_sim_py:main'`；依赖 `rclpy + sensor_msgs`（ament_python）。

### 23.4.5 GNSS 案例 · C++（cpp05_gnss_demo）

完整源码 `src/gnss_demo.cpp`：

```cpp
/*
    需求：GNSS 案例 —— 订阅 NavSatFix(经纬度) 数据，以首个坐标为原点，
          组织成 Path 并发布(便于在 rviz2 中查看轨迹)。
    流程：
        1.包含头文件；
        2.初始化 ROS2 客户端；
        3.自定义节点类；
            3-1.Path 数据组织之标头；
            3-2.Path 数据组织之坐标系；
            3-3.Path 数据组织之原点确定；
            3-4.Path 数据组织之经纬度。
        4.调用spin函数，并传入节点对象指针；
        5.释放资源。
*/
// 1.包含头文件；
#include "rclcpp/rclcpp.hpp"
#include "sensor_msgs/msg/nav_sat_fix.hpp"
#include "nav_msgs/msg/path.hpp"
#include "cmath"

using std::placeholders::_1;

// 3.自定义节点类；
class Gnss2Path: public rclcpp::Node{
public:
    Gnss2Path():Node("gnss_node_cpp"){
        RCLCPP_INFO(this->get_logger(),"GNSS 案例节点创建!");
        // 3-1.订阅 GNSS 数据；
        gnss_sub_ = this->create_subscription<sensor_msgs::msg::NavSatFix>("fix",10,
            std::bind(&Gnss2Path::gnss_callback,this,_1));
        // 3-2.发布轨迹；
        path_pub_ = this->create_publisher<nav_msgs::msg::Path>("gnss_path",10);
        path_.header.frame_id = "map";
        has_origin_ = false;
    }
private:
    void gnss_callback(const sensor_msgs::msg::NavSatFix::SharedPtr fix){
        // 3-3.原点确定(以首个有效坐标为原点)；
        if (!has_origin_) {
            if (fix->status.status < 0 || std::abs(fix->latitude) < 1e-9) {
                return;
            }
            origin_lat_ = fix->latitude;
            origin_lon_ = fix->longitude;
            has_origin_ = true;
            RCLCPP_INFO(this->get_logger(),"定位原点:(%.6f,%.6f)",origin_lat_,origin_lon_);
        }
        // 3-4.经纬度 -> 平面坐标(米)，等距圆柱近似；
        double dlat = fix->latitude - origin_lat_;
        double dlon = fix->longitude - origin_lon_;
        double x = dlon * 111319.49079327358 * std::cos(origin_lat_ * M_PI / 180.0);
        double y = dlat * 111319.49079327358;

        geometry_msgs::msg::PoseStamped pose;
        pose.header.frame_id = "map";
        pose.header.stamp = this->now();
        pose.pose.position.x = x;
        pose.pose.position.y = y;
        path_.poses.push_back(pose);
        path_.header.stamp = this->now();
        path_pub_->publish(path_);
    }
    rclcpp::Subscription<sensor_msgs::msg::NavSatFix>::SharedPtr gnss_sub_;
    rclcpp::Publisher<nav_msgs::msg::Path>::SharedPtr path_pub_;
    nav_msgs::msg::Path path_;
    bool has_origin_;
    double origin_lat_ = 0.0;
    double origin_lon_ = 0.0;
};

int main(int argc, char ** argv)
{
    rclcpp::init(argc,argv);
    rclcpp::spin(std::make_shared<Gnss2Path>());
    rclcpp::shutdown();
    return 0;
}
```

分步讲解（对照视频 C++ 六讲）：

- **01 框架搭建**：订阅 `fix`、发布 `gnss_path`；成员变量持有 `path_`（轨迹累加器）、`has_origin_` 与原点经纬度。
- **02 标头**：构造函数里 `path_.header.frame_id = "map"`——rviz2 的 Fixed Frame 设为 map 即可显示；Path 的 header 只需设置一次。
- **03 坐标系**：目标平面系取「x 向东、y 向北」的局部 ENU 约定，与 rviz2 右手系显示一致。
- **04 原点确定**：仅当 `status >= 0`（已定位）且纬度非零才把首帧采纳为原点，避免把 NO_FIX 状态下的 (0,0) 钉成原点；成功后打印原点经纬度。
- **05 经纬度换算**：纬度差 × 111319.49079327358 m 得 y（南北向）；经度差 × 同系数 × cos(原点纬度) 得 x（东西向，纬度越高每度经线越短）。等距圆柱近似在数公里内误差可忽略。
- **06 完成与小结**：每个有效 `/fix` 生成 `PoseStamped`（只填 position.x/y）追加进 `path_.poses`，刷新标头时间戳后整体重发——Path 是「全量轨迹」语义，订阅方每次收到累计折线。

`CMakeLists.txt` 在相机包基础上增加 `find_package(nav_msgs REQUIRED)`、`find_package(geometry_msgs REQUIRED)`，并 `ament_target_dependencies(gnss_demo rclcpp sensor_msgs nav_msgs geometry_msgs)`；`package.xml` 对应声明三个 `<depend>`。

### 23.4.6 GNSS 案例 · Python（py05_gnss_demo）

完整源码 `py05_gnss_demo/gnss_demo_py.py`：

```python
# -*- coding: utf-8 -*-
"""
    需求：GNSS 案例（Python实现）—— 订阅 NavSatFix，以首个有效坐标为原点组织 Path 发布。
"""
import math

import rclpy
from geometry_msgs.msg import PoseStamped
from nav_msgs.msg import Path
from rclpy.node import Node
from sensor_msgs.msg import NavSatFix


class Gnss2PathPy(Node):

    def __init__(self):
        super().__init__("gnss_node_py")
        self.get_logger().info("GNSS 案例节点创建!(python)")
        self.sub = self.create_subscription(NavSatFix, "fix", self.gnss_callback, 10)
        self.pub = self.create_publisher(Path, "gnss_path", 10)
        self.path = Path()
        self.path.header.frame_id = "map"
        self.has_origin = False
        self.origin_lat = 0.0
        self.origin_lon = 0.0

    def gnss_callback(self, fix):
        # 原点确定(以首个有效坐标为原点)；
        if not self.has_origin:
            if fix.status.status < 0 or abs(fix.latitude) < 1e-9:
                return
            self.origin_lat = fix.latitude
            self.origin_lon = fix.longitude
            self.has_origin = True
            self.get_logger().info("定位原点:(%.6f,%.6f)" % (self.origin_lat, self.origin_lon))
        # 经纬度 -> 平面坐标(米)，等距圆柱近似；
        dlat = fix.latitude - self.origin_lat
        dlon = fix.longitude - self.origin_lon
        x = dlon * 111319.49079327358 * math.cos(math.radians(self.origin_lat))
        y = dlat * 111319.49079327358
        pose = PoseStamped()
        pose.header.frame_id = "map"
        pose.header.stamp = self.get_clock().now().to_msg()
        pose.pose.position.x = x
        pose.pose.position.y = y
        self.path.poses.append(pose)
        self.path.header.stamp = self.get_clock().now().to_msg()
        self.pub.publish(self.path)


def main():
    rclpy.init()
    rclpy.spin(Gnss2PathPy())
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

Python 三讲对照：01 框架搭建（订阅/发布/成员状态）→ 02 部分字段设置（`path.header.frame_id = "map"` 与原点状态量）→ 03 数据组织（有效性判别、`math.radians` 等价于 C++ 的 `* M_PI / 180.0`，追加发布）。入口 `gnss_demo_py`；依赖 `rclpy + sensor_msgs + nav_msgs + geometry_msgs`。

## 23.6 与 ROS2 / 机器人开发的关联

1. **sensor_msgs 消息族全景成型**：本章补全 `Image`/`CameraInfo`、`Imu`、`NavSatFix`，与上一章 `LaserScan`/`PointCloud2` 共同构成机器人感知接口层；`header.frame_id` + `header.stamp` 是它们接入 tf2 与消息滤波器（`message_filters` 时间同步）的钥匙。
2. **tf2 坐标树的传感器挂载**：每类传感器都需要 `base_link → <sensor_link>` 的静态变换（URDF 或 `static_transform_publisher`）；EKF 融合后还要理清谁发布 `odom → base_link`，这是导航场景 tf 冲突的头号来源。
3. **nav2 的输入质量决定导航质量**：Nav2 的代价地图（costmap）用 `/scan` 或 `/points`，AMCL 用 `/scan` + `/odom`，`controller_server` 用融合里程计。本章的过滤/融合/标定直接决定导航是否抖动、是否撞障。
4. **robot_localization 是导航前的必修课**：EKF 输出的 `/odometry/filtered` 建议作为 Nav2 的标准里程计输入；对 GNSS 机器人，`navsat_transform_node` + 双 EKF 是室外导航的标配架构。
5. **image_transport / cv_bridge 生态**：`Image` 只是裸字节，压缩图传、去畸变、相机标定全部围绕 `image_transport` 插件体系与 `CameraInfo` 展开；本章相机仿真发布的 `/image_raw` 可直接接入这套生态（rqt_image_view 可显示、`compressed` 插件可订阅）。
6. **仿真 → 实机迁移**：标定参数（轮径、轮距、相机内参、IMU 零偏）是纯「实机量」，仿真里永远拿不到；建立标定流程意识，比记住某个系数更重要。

## 23.7 自测与练习

1. **概念题**：`sensor_msgs/Image` 的 `encoding` 为 `bgr8` 时，`data` 中每个像素的三个字节分别是什么通道？与 `rgb8` 相比，直接用 numpy 按 `rgb` 显示会怎样？
2. **计算题**：一个 rgb8 编码、640×480 的 Image，`step` 与 `data` 长度各是多少？若改为 mono8 又各是多少？
3. **概念题**：`sensor_msgs/Imu` 中 `orientation_covariance[0] = -1` 表示什么？`linear_acceleration.z` 在传感器静止水平放置时应约为多少？
4. **概念题**：`NavSatFix.status.status = -1` 时回调应如何处理？本仓库 gnss_demo 的判别条件是哪两个？
5. **动手任务**：把 cpp03_camera_sim 的 encoding 改为 `rgb8` 并让条纹变成红蓝交替（data 每 3 字节一组），重编后用 `--no-arr` echo 验证 step 与 data 长度的变化。
6. **动手任务**：搭建双雷达融合环境（仿真中用两个 `laserscan` 插件分别朝前、朝后），经 `laserscan_multi_merger` 输出 360° 融合扫描。验收标准：rviz2 中两个雷达的障碍物点云无缝拼接，`tf2_echo base_link laser_front_link` 有稳定输出。
7. **动手任务**：完成轮式里程计线性标定：命令机器人直行 5 m（仿真或实机），记录 `/odom` 推算距离，计算修正系数并应用，复测 3 次误差 < 5%。

> 参考答案要点：1. 依次为蓝、绿、红通道；按 `rgb` 解释会蓝红互换（天空变红）。2. rgb8：step = 640×3 = 1920，data 长 = 1920×480 = 921600；mono8：step = 640，data 长 = 307200。3. 表示该 IMU 无姿态输出能力，融合时不能使用其绝对姿态；z 轴约 +9.81 m/s²（测到的是比力，含重力）。4. 视为无效直接丢弃（return）；条件是 `status.status < 0 || abs(latitude) < 1e-9`。5. step = 960、data 长 = 230400；注意 `step = width * 3` 且 `(c/20)%2` 控制的是像素列而非字节列。6. 融合前必须有 `base_link → laser_*_link` 静态 tf 且两路 scan 时间戳有效；无缝拼接的关键是安装角与 tf 精确。7. 修正系数 = 目标距离 / 实测里程计距离，乘到底盘轮径参数上；多次实验取平均以抑制打滑误差。

## 23.8 常见问题（FAQ）

- **Q：`/image_raw` 能收到但显示花屏？** A：多为 `encoding` 与实际数据不符（如相机输出 YUYV 却声明 rgb8），或 `step` 计算错误（忽略行对齐）；用 `ros2 topic echo /image_raw --field encoding` 核对，`usb_cam` 中显式设置 `pixel_format`。
- **Q：`ros2 topic echo /gnss_path` 报 does not appear to be published yet？** A：echo 时轨迹节点没在运行，DDS 发现不到发布者（本章实测日志 `gnss_path_echo.log` 复现了该现象）。先启动 `gnss_demo` 与 `/fix` 数据源，再另开终端 echo。
- **Q：Python 版节点被 Ctrl+C 或 timeout 结束时打印 `ExternalShutdownException` / `KeyboardInterrupt` 堆栈？** A：这是 rclpy 在外部信号打断 spin 时的已知表现（本章 `py03/py04/py05` 实测日志均有记录），不影响功能；想优雅退出可在 main 里 try/except 捕获后再 `rclpy.shutdown()`。
- **Q：IMU 日志刷屏太快怎么限频？** A：真实 IMU 常见 100–200 Hz，教学代码逐条打印会刷屏；C++ 用 `RCLCPP_INFO_THROTTLE(*get_logger(), *get_clock(), 1000, ...)`，Python 用 `get_logger().info(..., throttle_duration_sec=1.0)`。
- **Q：EKF 启动后 tf 报 `odom → base_link` 冲突/跳变？** A：底盘驱动与 `ekf_node` 同时发布了同一变换。二选一：底盘只发 `/odom` 话题不发 tf，由 EKF `publish_tf: true` 统一发布。
- **Q：GNSS 轨迹在 rviz2 中是个点？** A：经纬度未投影，数值量级（116°、39°）远超地图尺度。按首帧做 ENU 投影或使用 `navsat_transform_node`。
- **Q：多相机时 `/dev/video*` 顺序随机？** A：设备号按枚举顺序分配，插拔后会变。写 udev 规则按 USB 端口序列号固定符号链接（如 `/dev/camera_front`），launch 中用符号链接启动。
- **Q：雷达融合后 rviz2 中两圈扫描错位？** A：检查各雷达静态 tf 的平移/旋转是否与实际安装一致、`destination_frame` 是否为共同祖先（`base_link`）、两雷达驱动的系统时间是否同步（NTP/chrony）。

## 23.9 本章小结

- 相机/IMU/GNSS 的消息规范（Image/Imu/NavSatFix）是接入真实驱动前最好的「接口演练」：编码决定字节序与 step、四元数携带姿态、经纬度必须投影、状态位决定数据可用性；
- 单目相机仿真（发布方）与 IMU 解析（订阅方）合成一对最小闭环，GNSS→Path 演示「订阅 + 变换 + 发布」的完整加工范式，三者 C++/Python 双实现可在无硬件环境逐一复现；
- 轮式里程计标定（线性/角速度两步）与 robot_localization EKF 融合解决「算得稳」：修正系数来自实验，融合质量来自协方差配置与 tf 唯一性；
- 雷达工具链（laser_filters 过滤、ira_laser_tools 融合、laser_geometry/pointcloud_to_laserscan 互转）与相机进阶（远程图传、棋盘格标定、udev 多相机）把原始数据加工成 SLAM 与导航可直接消费的状态。
